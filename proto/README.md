# قراردادها: <span dir="ltr">`proto/`</span>

این پوشه مرجع همه‌ی قراردادهای بین سرویس‌هاست: فایل‌های Protobuf برای gRPC و REST، و JSON Schema رویدادها.

[مشخصات فنی، بخش ۶](../docs/SPEC.md) | [فصل ۶: API و قراردادها](../docs/guide/06-api-and-contracts.md) | [قواعد دستیار AI](../AGENTS.md)

## ۱. چه چیزی از اینجا ساخته می‌شود

از هر فایل proto با `buf` چهار چیز ساخته می‌شود: کد Go برای سرور و client gRPC، کد grpc-gateway برای مسیرهای REST در `gateway`، سند OpenAPI در `docs/api/openapi.yaml` (که کلاینت TypeScript فرانت از آن ساخته می‌شود)، و stub پایتون برای سرویس `ai`. پس یک تغییر کوچک اینجا به سه بخش تیم می‌رسد. کد تولیدی را هیچ‌وقت با دست ویرایش نکن.

## ۲. ساختار پوشه

</div>

```text
proto/
├── buf.yaml
├── sarmiz/
│   ├── identity/v1/*.proto
│   ├── catalog/v1/*.proto
│   └── order/v1/*.proto
└── events/*.schema.json
```

<div dir="rtl">

`gateway` و `realtime` سرویس gRPC کسب‌وکاری ندارند و `ai` با HTTP داخلی کار می‌کند، پس پوشه‌ی proto ندارند. تنظیمات تولید کد و جای خروجی‌ها را تیم در `W1-PA-3` تعیین می‌کند.

## ۳. نام‌گذاری

| چیز | قاعده | منبع |
|---|---|---|
| بسته | `sarmiz.<service>.v1` | مشخصات فنی ۶٫۲ |
| سرویس و متد | همان نام‌های جدول بخش ۶٫۲، مثل `OrderService.CreateOrder` | مشخصات فنی ۶٫۲ |
| فیلد | `snake_case`؛ پول `int64` با پسوند `_rial`؛ شناسه رشته‌ی UUID | مشخصات فنی ۶٫۱ |
| مسیر HTTP | annotation `google.api.http` با مسیرهای <span dir="ltr">`/api/v1`</span> جدول بخش ۶٫۱ | مشخصات فنی ۶٫۱ |
| اعتبارسنجی | قواعد `protovalidate` روی هر فیلد ورودی | مشخصات فنی ۶٫۲ |
| نام فایل | پیشنهاد اولیه: یک فایل برای هر سرویس gRPC، مثل `auth_service.proto` | تیم در `W1-PA-3` |

متدهای داخلی، مثل `PriceItems` و `GetMenuSnapshot`، annotation HTTP ندارند تا از بیرون در دسترس نباشند.

## ۴. گردش کار `buf`

1. فایل proto را عوض کن.
2. `buf lint` را اجرا کن.
3. `buf breaking` را در برابر `main` اجرا کن تا ببینی چیزی از قرارداد قبلی شکسته است یا نه.
4. کد را دوباره بساز؛ `docs/api/openapi.yaml` هم دوباره ساخته می‌شود.
5. کد تولیدی و `openapi.yaml` را در همان PR commit کن.

دستور دقیق هر قدم را تیم در هفته‌ی ۱ می‌سازد و در بخش Commands فایل [AGENTS.md](../AGENTS.md) می‌نویسد. CI همین قدم‌ها را روی هر PR اجرا می‌کند و اگر `openapi.yaml` ساخته‌شده با نسخه‌ی commit‌شده فرق کند، خطا می‌دهد.

## ۵. JSON Schema رویدادها

برای هر subject جدول بخش ۶٫۳ یک فایل در <span dir="ltr">`proto/events/`</span> هست. پیشنهاد اولیه برای نام فایل: خود subject، مثل `sarmiz.order.order.created.schema.json`. هر schema دو چیز را می‌سنجد: envelope مشترک (`id`، `type`، `version`، `time`، `venue_id`، `trace_id`، `data`) و فیلدهای `data` همان رویداد. سرویسی که رویداد را منتشر می‌کند صاحب schema آن است و تست قرارداد هر رویداد منتشرشده را با schema می‌سنجد.

## ۶. تغییر امن قرارداد

| می‌خواهی | درست | غلط |
|---|---|---|
| فیلد اضافه کنی | شماره‌ی تازه، اختیاری برای clientهای قدیمی | استفاده از شماره‌ی یک فیلد حذف‌شده |
| فیلد حذف کنی | اول مصرف‌کننده‌ها را عوض کن، بعد حذف کن و شماره و نام را `reserved` کن | حذف یک‌باره در حالی که کسی هنوز می‌خواندش |
| نام یا نوع عوض کنی | فیلد تازه بساز، هر دو را مدتی پر کن، بعد قدیمی را حذف کن | تغییر درجا |
| شکل `data` رویداد را عوض کنی | افزودن فیلد آزاد است؛ تغییر ناسازگار یعنی `version` تازه و مصرف‌کننده‌ای که هر دو را می‌فهمد | تغییر معنی یک فیلد بدون نسخه‌ی تازه |

هیچ‌وقت شماره‌ی فیلد را دوباره استفاده یا عوض نکن. اگر واقعاً لازم است `buf breaking` را نادیده بگیری، اول با منتور حرف بزن. هر تغییری که با بخش ۶ مشخصات فنی فرق کند، سند تصمیم در <span dir="ltr">`docs/decisions/`</span> می‌خواهد.

## ۷. چه کسی بازبینی می‌کند

| مسیر | نویسنده | بازبین |
|---|---|---|
| <span dir="ltr">`sarmiz/identity/v1/`</span>، <span dir="ltr">`sarmiz/catalog/v1/`</span> | هسته | فرانت، سفارش، پلتفرم |
| <span dir="ltr">`sarmiz/order/v1/`</span> | سفارش | هسته، فرانت، پلتفرم |
| <span dir="ltr">`events/`</span> | بخشِ منتشرکننده | بخش‌های مصرف‌کننده |
| `buf.yaml` و تنظیمات تولید کد | پلتفرم | یک زوج دیگر |
| هر چیزی درباره‌ی ورود یا پرداخت | بخش صاحب آن | منتور هم |
