# تست

این فصل به یک سؤال جواب می‌دهد: از کجا بدانی سرمیز درست کار می‌کند، در هر سطح چه چیزی را با چه ابزاری تست کنی، و تست خوب با تستی که فقط سبز می‌شود چه فرقی دارد؟

[بازگشت به فهرست مستندات](../README.md)

## ۱. چرا مهم است

سرمیز شش سرویس دارد که هر کدام جدا مستقر می‌شوند، و بخش بزرگی از کدش را دستیار AI می‌نویسد. کامپایلر Go نمی‌فهمد که `order` فیلدی از `catalog` می‌خواهد که دیگر وجود ندارد، یا queryای `venue_id` را جا انداخته و سفارش کافه‌ی «الف» را روی صفحه‌ی آشپزخانه‌ی کافه‌ی «ب» می‌برد. تنها چیزی که این‌ها را قبل از مهمان و صاحب کسب‌وکار می‌گیرد، تست است. برای همین در سرمیز کاری که تستش در همان PR نیست، تمام‌شده حساب نمی‌شود.

## ۲. تصمیم‌ها در یک نگاه

| موضوع | تصمیم | چرا |
|---|---|---|
| تست واحد | قواعد کاری در پکیج‌های `service`، به شکل table-driven (تست جدولی)، همیشه با <span dir="ltr">`-race`</span>؛ هدف پوشش ۷۰٪ همان‌جا | قیمت، وضعیت سفارش و نقش‌ها مهم‌ترین و ارزان‌ترین چیز برای تست‌اند |
| تست یکپارچه | PostgreSQL، Redis و NATS واقعی با testcontainers-go یا Compose در CI | دیتابیس جعلی خطای SQL و تراکنش را نمی‌بیند |
| تست قرارداد | `buf lint` و `buf breaking`، JSON Schema رویدادها، diff فایل OpenAPI | سرویس‌ها جدا مستقر می‌شوند و کامپایلر شکستن قرارداد را نمی‌بیند |
| end-to-end | Playwright برای سه مسیر اصلی | کل زنجیره از دید کاربر کار کند |
| امنیت | مجموعه‌ی جداسازی در <span dir="ltr">`tests/isolation/`</span>: دو کسب‌وکار، همه‌ی endpointهای پنل، جدول نقش‌ها، محدودیت نرخ | نشت داده بین کسب‌وکارها بدترین خطای ممکن است |
| بار | k6 برای منوی عمومی، ساخت سفارش و پخش WebSocket در برابر هدف‌های بخش ۳ مشخصات فنی | عددهای طراحی باید اندازه گرفته شوند، نه فرض |
| AI | نمونه‌ی ترجمه، دقت import روی ۵ منوی واقعی، ۳۰ سؤال دستیار؛ مدل در تست واحد mock می‌شود | خروجی مدل قطعی نیست و باید با عدد سنجیده شود |
| تعریف «تمام شد» | تست‌های هر کار در همان PR | تستِ «بعداً» هیچ‌وقت نوشته نمی‌شود |

## ۳. هرم تست سرمیز

پایه‌ی هرم تست‌های زیاد، سریع و ارزان‌اند؛ هرچه بالاتر بروی تست‌ها کمتر، کندتر و گران‌ترند. هرم برعکس (چند تست end-to-end و تقریباً هیچ تست واحد) یعنی هر خطا را دیر و با زحمت پیدا می‌کنی.

| سطح | چه چیزی | ابزار | فایل‌ها کجا | کی اجرا می‌شود |
|---|---|---|---|---|
| واحد | قیمت‌گذاری، دو ماشین وضعیت، جدول نقش‌ها، fallback زبان، قواعد OTP | `go test -race`، pytest، Vitest و Testing Library | کنار کد: `services/<name>/internal/service/*_test.go`، داخل <span dir="ltr">`web/`</span> و <span dir="ltr">`services/ai/`</span> | هر PR، فقط سرویس‌های تغییرکرده |
| یکپارچه | repository، migration، outbox و relay، مصرف‌کننده‌ی رویداد، Redis | testcontainers-go یا Compose | کنار کد، مثلاً `internal/repository/*_test.go` | هر PR |
| قرارداد | proto، schema رویدادها، OpenAPI | `buf`، تست schema | <span dir="ltr">`proto/`</span>، <span dir="ltr">`proto/events/`</span>، `docs/api/openapi.yaml` | هر PR که این‌ها را عوض کند |
| end-to-end | سه مسیر اصلی | Playwright | <span dir="ltr">`tests/e2e/`</span> | پیشنهاد اولیه: بعد از هر استقرار روی `staging` |
| امنیت | جداسازی، نقش‌ها، محدودیت نرخ | تست Go | <span dir="ltr">`tests/isolation/`</span> | در CI (`W4-PA-3`) |
| بار | منوی عمومی، ساخت سفارش، WebSocket | k6 | <span dir="ltr">`tests/load/`</span> | دستی روی `staging`: هفته‌ی ۳ و قبل از انتشار |
| AI | ترجمه، import، دستیار | pytest با fixture (داده‌ی آماده‌ی تست) | داخل <span dir="ltr">`services/ai/`</span>، نتیجه در <span dir="ltr">`docs/ai/`</span> | دستی، هر بار که مدل یا prompt عوض شود |

ساختار پوشه‌ی <span dir="ltr">`tests/`</span> در [README تست‌ها](../../tests/README.md) آمده است.

## ۴. تست واحد قواعد کاری

قواعد کاری در لایه‌ی `service` هستند، پس بدون دیتابیس و شبکه تست می‌شوند. وابستگی‌ها (repository، کلاینت `catalog`، ساعت) پشت interface هستند و در تست با نسخه‌ی جعلی عوض می‌شوند. مثال: ماشین وضعیت سفارش از بخش ۷٫۳ مشخصات فنی.

</div>

```go
// example only: real names come from W1-ORD-1
func TestCanTransition(t *testing.T) {
	cases := []struct{ from, to Status; want bool }{
		{AwaitingPayment, Pending, true},
		{Pending, Accepted, true},
		{Accepted, Cancelled, true},
		{Preparing, Cancelled, false},
		{AwaitingPayment, Accepted, false},
		{Served, Pending, false},
	}
	for _, c := range cases {
		if got := CanTransition(c.from, c.to); got != c.want {
			t.Errorf("%s -> %s: got %v, want %v", c.from, c.to, got, c.want)
		}
	}
}
```

<div dir="rtl">

- هر ردیف یک قاعده از مشخصات فنی است. حالت‌های ممنوع به اندازه‌ی مجازها مهم‌اند: `preparing` به `cancelled` نمی‌رود و از `served` هیچ راهی نیست.
- زمان را تزریق کن. لغو خودکار سفارش آنلاین بعد از ۱۵ دقیقه یا انقضای کد بعد از ۱۲۰ ثانیه را با ساعت جعلی تست کن، نه با `time.Sleep`.

| سرویس | قاعده‌هایی که حتماً تست واحد می‌خواهند |
|---|---|
| `identity` | ۵ تلاش برای هر کد، چرخش توکن تازه‌سازی، باطل شدن خانواده با استفاده‌ی دوباره |
| `catalog` | `min_select` و `max_select`، `price_delta_rial`، fallback زبان، مقدارهای مجاز برچسب‌ها، منوی زمان‌دار |
| `order` | دو ماشین وضعیت، جمع سفارش از قیمت‌های `PriceItems`، شرط `StartPayment`، لغو بعد از ۱۵ دقیقه |
| `gateway` و `ai` | نقش لازم برای هر مسیر و قالب یکسان خطا؛ اعتبارسنجی خروجی مدل با Pydantic و `LLMProvider` جعلی |

## ۵. تست یکپارچه

تست یکپارچه سرویس را به PostgreSQL، Redis و NATS **واقعی** وصل می‌کند. دیتابیس جعلی نمی‌فهمد migration روی PostgreSQL اجرا نمی‌شود یا `FOR UPDATE` قفل نمی‌گیرد. testcontainers-go برای تست container بالا می‌آورد؛ در CI می‌شود از همان Compose محیط محلی (`W1-PA-1`) هم استفاده کرد. ابزار کمکی مشترک در `libs/go/kit` است، نه کپی در هر سرویس.

- هر متد repository، با این بررسی که با `venue_id` دیگر هیچ ردیفی برنگردد.
- migrationها: `up` روی دیتابیس خالی، `down`، و دوباره `up`. در Redis: کلید <span dir="ltr">`otp:{phone}`</span> با TTL ۱۲۰ ثانیه و hash کد، نه خود کد.
- outbox: تغییر و ردیف `outbox` با هم commit یا با هم rollback می‌شوند؛ relay رویداد را روی subject درست منتشر می‌کند.
- مصرف‌کننده: یک رویداد را دو بار بفرست؛ اثرش فقط یک بار دیده شود (`processed_events`).
- هم‌زمانی: ۲۰ `CreateOrder` هم‌زمان ۲۰ `code` متفاوت می‌دهد؛ دو callback هم‌زمان برای یک `authority` فقط یک پرداخت `verified` می‌سازد.
- هر تست کسب‌وکار خودش را با `venue_id` تصادفی می‌سازد تا تست‌ها موازی اجرا شوند و به ترتیب اجرا وابسته نباشند.

## ۶. تست قرارداد

در یک برنامه‌ی تک‌تکه، با عوض کردن نام یک فیلد کامپایلر همه‌ی جاهای استفاده را نشان می‌دهد. در میکروسرویس، `order` با نسخه‌ی قبلی proto ساخته و جدا مستقر شده است؛ شکستن قرارداد را در `staging` یا بدتر، در `production` می‌بینی. تست قرارداد این را به زمان PR می‌آورد.

| قرارداد | چه چیزی بررسی می‌شود | روش |
|---|---|---|
| proto | سبک و نام‌گذاری؛ حذف یا شماره‌گذاری دوباره‌ی فیلد | `buf lint` و <span dir="ltr">`buf breaking --against '.git#branch=main'`</span> |
| رویدادها | payload ساخته‌شده با schema در <span dir="ltr">`proto/events/`</span> می‌خواند؛ مصرف‌کننده نمونه‌ی معتبر را می‌فهمد | تست Go در منتشرکننده و مصرف‌کننده |
| OpenAPI | فایل ساخته‌شده با `docs/api/openapi.yaml` یکی است | CI فایل را دوباره می‌سازد و اگر `git diff` خالی نباشد شکست می‌خورد |

تست schema دو طرف دارد: `order` نشان می‌دهد رویداد `sarmiz.order.order.created` که می‌سازد با schema معتبر است، و `realtime` نشان می‌دهد نمونه‌ی معتبر همان schema را درست پخش می‌کند. کتابخانه‌ی اعتبارسنجی JSON Schema را زوج‌های سفارش و پلتفرم در `W1-ORD-4` انتخاب می‌کنند.

## ۷. سه مسیر end-to-end

`W5-WEB-5` این سه مسیر را با Playwright در <span dir="ltr">`tests/e2e/`</span> می‌نویسد. عنصرها را با نقش و برچسب پیدا کن (`getByRole`)، نه با کلاس CSS، و به‌جای `waitForTimeout` منتظر ظاهر شدن چیزی بمان.

**مسیر ۱: صاحب کسب‌وکار ثبت‌نام می‌کند و منو را منتشر می‌کند**

1. در <span dir="ltr">`/panel`</span> شماره‌ی آزمایشی را وارد کن، کد را از SMS جعلی بگیر (بخش ۱۳) و وارد شو.
2. کسب‌وکار بساز؛ پنل بدون ورود دوباره نقش `owner` را دارد.
3. یک دسته، یک آیتم با قیمت و یک گروه گزینه، و یک میز بساز.
4. لینک QR میز را در یک context تازه (مرورگر بدون کوکی) باز کن: آیتم با همان قیمت به تومان دیده می‌شود.

**مسیر ۲: مهمان با پرداخت در صندوق سفارش می‌دهد و آشپزخانه وضعیت را عوض می‌کند**

1. دو context باز کن: مهمان روی <span dir="ltr">`/t/:qrToken`</span> و کارمند روی <span dir="ltr">`/panel/kitchen`</span>.
2. مهمان آیتمی با گزینه سفارش می‌دهد و پرداخت در صندوق را انتخاب می‌کند؛ <span dir="ltr">`/o/:orderId`</span> وضعیت `pending` را نشان می‌دهد.
3. سفارش در کمتر از ۲ ثانیه روی صفحه‌ی آشپزخانه ظاهر می‌شود.
4. کارمند وضعیت را به `accepted`، `preparing` و `ready` می‌برد؛ صفحه‌ی مهمان هر تغییر را بدون refresh نشان می‌دهد.
5. کارمند پرداخت در صندوق را ثبت می‌کند.

**مسیر ۳: مهمان در حالت sandbox آنلاین پرداخت می‌کند**

1. مهمان سفارش آنلاین ثبت می‌کند؛ وضعیت `awaiting_payment` است و صفحه‌ی آشپزخانه آن را **نمی‌بیند**.
2. دکمه‌ی پرداخت مهمان را به درگاه می‌برد و پرداخت موفق می‌شود.
3. بعد از callback، صفحه‌ی نتیجه پرداخت موفق را نشان می‌دهد و سفارش با `pending` روی صفحه‌ی آشپزخانه می‌آید.
4. نشانی callback را دوباره باز کن: همان نتیجه برمی‌گردد و فقط یک پرداخت `verified` وجود دارد.

> [!NOTE]
> مشخصات فنی نگفته تست end-to-end کد ورود را در `staging` از کجا بگیرد و مسیر ۳ با درگاه جعلی اجرا شود یا sandbox واقعی. پیشنهاد اولیه: اجرای خودکار با SMS و درگاه جعلی، و مسیر ۳ هفته‌ای یک بار دستی با sandbox روی `staging`. تیم این را در هفته‌ی ۵ تصمیم می‌گیرد.

## ۸. مجموعه‌ی جداسازی کسب‌وکارها و جدول نقش‌ها

`W4-PA-3` در <span dir="ltr">`tests/isolation/`</span> تست‌های Go می‌نویسد که مثل یک کاربر بیرونی، از راه `gateway` درخواست می‌زنند. دو کسب‌وکار A و B ساخته می‌شوند، هر دو با میز، منو، سفارش و درخواست خدمت. کاربرها: `ownerA`، `managerA` و `staffA` با سه نقش در A، و `ownerB` در B.

1. **بین کسب‌وکارها.** برای **هر** endpoint زیر <span dir="ltr">`/venues/{venue_id}/*`</span>، `ownerA` یک بار با `venue_id` کسب‌وکار B درخواست می‌زند، و یک بار با `venue_id` خودش ولی شناسه‌ی منبعی از B (مثلاً آیتم منوی B). جواب درست در هر دو حالت `404` با کد `not_found` است، و داده‌ی B نباید عوض شده باشد.
2. **جدول نقش‌ها.** هر ردیف جدول بخش ۸ مشخصات فنی یک آزمون است:

| درخواست در کسب‌وکار A | `ownerA` | `managerA` | `staffA` |
|---|---|---|---|
| تغییر وضعیت سفارش، تغییر موجودی | مجاز | مجاز | مجاز |
| ویرایش منو، میز یا QR | مجاز | مجاز | `403` |
| گزارش فروش | مجاز | مجاز | `403` |
| تنظیم پرداخت | مجاز | `403` | `403` |
| هر مسیر <span dir="ltr">`/admin/*`</span> | `403` | `403` | `403` |

3. **مسیرهای عمومی.** `order_token` سفارش A سفارش B را باز نمی‌کند؛ `qr_token` میز A با آیتم منوی B سفارش نمی‌سازد؛ ششمین سفارش یک guest session در ۵ دقیقه `429` با `Retry-After` می‌گیرد.

«همه‌ی endpointها» را دستی فهرست نکن، چون endpoint تازه جا می‌ماند. پیشنهاد اولیه: تست فهرست مسیرهای <span dir="ltr">`/venues/{venue_id}/*`</span> را از `docs/api/openapi.yaml` بخواند و برای هر کدام یک زیرتست (`t.Run`) بسازد؛ این‌طور هر endpoint تازه خودبه‌خود آزموده می‌شود و کسی لازم نیست یادش بماند.

## ۹. آزمون بار با k6

`W3-PA-3` سه سناریو در <span dir="ltr">`tests/load/`</span> می‌نویسد و گزارش کتبی می‌دهد. معیار قبولی همان هدف‌های بخش ۳ مشخصات فنی است:

| سناریو | بار | معیار قبولی |
|---|---|---|
| منوی عمومی | ۵۰۰ مهمان هم‌زمان روی منوی چند کسب‌وکار | p95 زیر ۳۰۰ میلی‌ثانیه در `gateway` |
| ساخت سفارش | ۲۰ سفارش در دقیقه، و یک بار چند برابر آن | p95 زیر ۸۰۰ میلی‌ثانیه |
| پخش WebSocket | ۱۰۰ اتصال پنل و ۵۰۰ اتصال مهمان | سفارش در کمتر از ۲ ثانیه به صفحه‌ی آشپزخانه می‌رسد |

</div>

```ts
// tests/load/public-menu.ts (example only)
import http from 'k6/http';
import { sleep } from 'k6';
export const options = {
  vus: 500,
  duration: '5m',
  thresholds: { http_req_duration: ['p(95)<300'], http_req_failed: ['rate<0.01'] },
};
export default function () {
  http.get(`${__ENV.BASE_URL}/api/v1/public/t/${__ENV.QR_TOKEN}`);
  sleep(Math.random() * 5);
}
```

<div dir="rtl">

- آستانه‌ی خطای ۱٪ پیشنهاد اولیه است؛ مشخصات فنی برای آزمون بار عدد خطا نداده است. روی `production` آزمون بار نزن، و بار را از ماشینی جدا از سرور بفرست؛ k6 روی همان سرور CPU را از سرویس‌ها می‌گیرد و عدد را خراب می‌کند.
- همه‌ی درخواست‌ها از یک IP می‌آیند و به محدودیت ۱۲۰ در دقیقه‌ی منوی عمومی می‌خورند. اینکه محدودیت‌ها در `staging` برای آزمون بالا برود یا IP آزمون مستثنا شود را تیم در هفته‌ی ۳ تصمیم می‌گیرد و در گزارش می‌نویسد.
- خواندن گزارش و انتخاب چیزی که باید درست شود در [فصل ۱۸](18-scaling-and-resilience.md) است.

## ۱۰. ارزیابی AI

خروجی مدل هر بار کمی فرق می‌کند، پس «سبز یا قرمز» کافی نیست و باید با عدد بسنجی. دو نوع تست جدا داری:

- **تست واحد `ai`** در هر PR، با `LLMProvider` جعلی که جواب ثابت می‌دهد: اعتبارسنجی Pydantic، رد خروجی خراب، timeout و شکل جواب.
- **مجموعه‌ی ارزیابی** با مدل واقعی روی Ollama، دستی: ترجمه برای هر زبان (`W3-PA-4`)، import روی ۵ منوی واقعی (`W1-PA-7`)، و ۳۰ سؤال دستیار شامل سؤال نامربوط و prompt injection (`W4-PA-4`، `W5-PA-1`). عددها در <span dir="ltr">`docs/ai/`</span> ثبت می‌شوند. جزئیات در [فصل ۱۹](19-ai-service.md).

## ۱۱. تست فرانت با Vitest و Testing Library

Testing Library تو را وادار می‌کند مثل کاربر به صفحه نگاه کنی: دکمه را با نقش و نام پیدا کن (`getByRole`)، نه با کلاس. API را در مرز کلاینت تولیدشده جعلی کن. این رفتارها در `web` تست واحد می‌خواهند:

- سبد در `localStorage` به ازای هر میز نگه داشته می‌شود و سبد دو میز قاطی نمی‌شود.
- برگه‌ی آیتم تا `min_select` گزینه انتخاب نشده اجازه‌ی افزودن نمی‌دهد.
- قیمت ریال با `Intl.NumberFormat` به تومان نشان داده می‌شود، و جهت صفحه از زبان می‌آید (`ar` و `ckb` راست‌به‌چپ، `en` چپ‌به‌راست).
- خطای API با قالب یکسان به پیام قابل‌فهم تبدیل می‌شود.

## ۱۲. race detector

<span dir="ltr">`-race`</span> در Go دسترسی هم‌زمان چند goroutine به یک حافظه بدون قفل (race) را پیدا می‌کند. جاهای حساس سرمیز: نقشه‌ی اتصال‌ها در hub سرویس `realtime`، کش JWKS در `gateway`، relay outbox. همه‌ی تست‌های Go در CI با <span dir="ltr">`go test -race -count=1 ./...`</span> اجرا می‌شوند. ولی race detector فقط raceای را می‌بیند که تست واقعاً اجرا کرده است. تست تک‌goroutine هیچ چیز پیدا نمی‌کند؛ برای کد هم‌زمان تستی بنویس که واقعاً چند goroutine را با هم راه بیندازد، مثلاً ۵۰ اتصال که هم‌زمان وصل و قطع می‌شوند و هم‌زمان رویداد می‌گیرند.

## ۱۳. داده‌ی تست، fixture و سرویس‌های جعلی

| چیز | کجا | قاعده |
|---|---|---|
| داده‌ی نمونه‌ی محلی | اسکریپت `W2-PA-5` | یک کسب‌وکار نمایشی با منوی کامل، با یک دستور |
| fixture و سازنده‌ی داده | <span dir="ltr">`testdata/`</span> کنار تست، ابزار تست در `libs/go/kit` | پیشنهاد اولیه: تابعی که کسب‌وکار با `slug` و `venue_id` تصادفی، میز و منو می‌سازد |
| SMS جعلی | پشت interface پیامک (`W1-CORE-2`) | محلی: کد در لاگ چاپ می‌شود. در تست: نسخه‌ی حافظه‌ای که آخرین کد هر شماره را نگه می‌دارد |
| درگاه جعلی | پشت `PaymentProvider` (`W3-ORD-4`) | قابل تنظیم برای موفق، ناموفق، timeout و callback تکراری |
| ساعت | interface ساعت در `service` | برای انقضا و لغو خودکار، زمان را جلو ببر |

- شماره‌ی موبایل واقعی، حتی شماره‌ی خودت، در تست و fixture نگذار؛ از شماره‌های ساختگی اسکریپت seed استفاده کن. SMS و درگاه جعلی فقط در `local` و تست فعال‌اند. سرویس در `production` نباید با پیاده‌سازی جعلی بالا بیاید.

## ۱۴. تست خوب و تستی که چیزی را نمی‌سنجد

دستیار AI و برنامه‌نویس تازه‌کار هر دو تستی می‌نویسند که سبز می‌شود ولی هیچ قاعده‌ای را نمی‌سنجد. سؤال اصلی: «اگر قاعده را در کد خراب کنم، این تست قرمز می‌شود؟»

</div>

```go
// bad: green even if the total is wrong
order, err := svc.CreateOrder(ctx, req)
if err != nil || order == nil {
	t.Fatal("create failed")
}

// good: 2 x (latte 450000 + extra shot 25000), computed by hand
if order.TotalRial != 950_000 {
	t.Fatalf("total_rial = %d, want 950000", order.TotalRial)
}
```

<div dir="rtl">

| الگوی بد | چرا چیزی نمی‌سنجد | به‌جایش |
|---|---|---|
| فقط بررسی `err == nil` | جمع اشتباه هم سبز است | مقدار مشخص قاعده را بسنج |
| حساب کردن انتظار با همان فرمول کد | اگر فرمول غلط باشد، تست هم غلط است | عدد صریحی که با دست حساب کرده‌ای |
| فقط مسیر موفق | قواعد سرمیز بیشتر درباره‌ی «نه» هستند | حالت‌های رد را هم بنویس |
| `time.Sleep` برای صبر کردن | گاهی سبز، گاهی قرمز | ساعت جعلی، یا صبر تا برقرار شدن شرط |
| `t.Skip` یا کامنت کردن تست قرمز | خطا پنهان می‌شود | درستش کن یا در PR بگو چرا |

آزمون ساده: قاعده را عمداً خراب کن (مثلاً `preparing` به `cancelled` را مجاز کن) و تست را اجرا کن. اگر سبز ماند، تست چیزی نمی‌سنجد.

## ۱۵. هدف پوشش، و «تمام شد» یعنی تست در همان PR

۷۰٪ هدفِ پکیج‌های `service` است، نه کل سرویس؛ با <span dir="ltr">`go test -race -coverprofile=cover.out ./internal/service/...`</span> و بعد `go tool cover -func=cover.out` ببینش. پوشش فقط می‌گوید کدام خط اجرا شد، نه اینکه چیزی بررسی شد؛ تست بدون assertion (بررسی نتیجه) هم پوشش را بالا می‌برد. جداسازی، هم‌زمانی و قرارداد بین سرویس‌ها در این عدد دیده نمی‌شوند. از عدد پوشش برای پیدا کردن کد بی‌تست استفاده کن، نه برای اثبات درستی. اینکه CI زیر ۷۰٪ را رد کند یا فقط گزارش دهد، در `W1-PA-5` تصمیم گرفته می‌شود.

مشخصات فنی می‌گوید کاری تمام است که تست‌هایش در همان PR باشد. یعنی: قاعده‌ی کاری تازه با تست واحد جدولی و حالت‌های رد؛ متد repository، migration یا endpoint تازه‌ی پنل با تست یکپارچه و بررسی `venue_id`؛ تغییر proto یا رویداد با `buf` سبز، OpenAPI ساخته‌شده و schema رویداد؛ صفحه‌ی وب با تست Vitest برای رفتار؛ کد پرداخت و ورود با تست هم‌زمانی و بازبینی منتور؛ و تغییر prompt یا مدل با اجرای دوباره‌ی ارزیابی و ثبت عدد در <span dir="ltr">`docs/ai/`</span>.

- [ ] مجموعه‌ی جداسازی همه‌ی endpointهای پنل و همه‌ی ردیف‌های جدول نقش‌ها را می‌پوشاند و در CI است.
- [ ] گزارش آزمون بار و نتیجه‌ی ارزیابی‌های AI با عدد نوشته شده‌اند.

## اشتباه‌های رایج

| اشتباه | چرا بد است | چه کار کن |
|---|---|---|
| «تست را در PR بعدی می‌نویسم» | PR بعدی هیچ‌وقت نمی‌آید | تست در همان PR، وگرنه کار تمام نیست |
| mock کردن دیتابیس برای repository | خطای SQL، تراکنش و قفل دیده نمی‌شود | تست یکپارچه با PostgreSQL واقعی |
| یک کسب‌وکار مشترک برای همه‌ی تست‌ها | تست‌ها به ترتیب اجرا وابسته می‌شوند | هر تست داده‌ی خودش را بسازد |
| قبول کردن `403` در تست جداسازی بین کسب‌وکارها | `403` نشان می‌دهد آن شناسه وجود دارد | فقط `404` با `not_found` قبول است |
| merge کردن تست‌های دستیار بدون خواندن | تستی که چیزی نمی‌سنجد سبز می‌شود | قاعده را عمداً خراب کن و ببین قرمز می‌شود |
| تست end-to-end برای قاعده‌ای که تست واحد کافی است | کند و شکننده | قاعده پایین هرم، مسیر کاربر بالای هرم |

## کار با AI روی این موضوع

**فایل‌هایی که به دستیار می‌دهی:** `AGENTS.md`، بخش ۱۳ و بخش مربوط به قاعده از `docs/SPEC.md`، همین فصل، فایل کدی که تست می‌شود و متن issue.

```text
کنار هر ردیف در یک کامنت کوتاه بنویس کدام جمله‌ی مشخصات فنی را می‌سنجد.
```

<div dir="rtl">

بازبینی تست‌های موجود:

</div>

```text
فایل‌های *_test.go این پوشه را بخوان. برای هر تست بگو:
۱. کدام قاعده از docs/SPEC.md را می‌سنجد
۲. اگر آن قاعده در کد خراب شود، این تست قرمز می‌شود یا نه
تست‌هایی را که چیزی نمی‌سنجند، انتظارشان را با فرمول خود کد حساب می‌کنند، یا time.Sleep دارند جدا فهرست کن.
کدی را تغییر نده.
```

<div dir="rtl">

**خودت حتماً بررسی کن:** هر عدد انتظار را خودت با دست حساب کن. یک بار قاعده را عمداً خراب کن و ببین تست قرمز می‌شود. `go test -race` را خودت اجرا کن، نه فقط CI. در fixtureهایی که دستیار ساخته دنبال شماره‌ی موبایل یا نام واقعی بگرد.
