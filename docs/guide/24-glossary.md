# واژه‌نامه

واژه‌هایی که در مستندات، issueها و جلسه‌های کار با AI می‌بینی، با معنی کوتاه و جایی که در سرمیز به کار می‌روند.

[بازگشت به فهرست مستندات](../README.md)

## ۱. پیش از استفاده

- واژه‌ها بر اساس حوزه دسته‌بندی شده‌اند. اگر واژه‌ای را پیدا نکردی، با Ctrl+F دنبالش بگرد؛ بعضی واژه‌ها به چند حوزه مربوط‌اند ولی فقط یک بار آمده‌اند.
- معنی‌ها کوتاه‌اند. تعریف دقیق هر قاعده در [مشخصات فنی](../SPEC.md) است و اگر این صفحه با آن فرق داشت، مشخصات فنی درست است.
- نام‌های فنی انگلیسی می‌مانند. برای واژه‌های محصول، معادل فارسی‌ای که در همه‌ی مستندات به کار می‌بریم کنار واژه‌ی انگلیسی آمده است.
- اگر واژه‌ای کم بود، در همان PR که اولین بار به کارش بردی اضافه‌اش کن.

## ۲. محصول

| واژه | معنی | در سرمیز |
|---|---|---|
| کسب‌وکار (venue) | حساب یک کافه یا رستوران | جدول `venues` در `catalog`؛ همه‌ی داده‌ها با `venue_id` جدا می‌شوند |
| شعبه (branch) | یک مکان فیزیکی کسب‌وکار | جدول `branches`؛ در انتشار ۱ هر کسب‌وکار دقیقاً یکی دارد |
| مهمان (guest) | مشتری‌ای که QR را اسکن می‌کند | بدون حساب؛ مسیرهای <span dir="ltr">`/t/:qrToken`</span>، <span dir="ltr">`/m/:slug`</span> و <span dir="ltr">`/o/:orderId`</span> |
| صاحب کسب‌وکار (owner) | کسی که کسب‌وکار را ساخته | نقش `owner`؛ تنها نقشی که رابط انتشار ۱ می‌سازد |
| پنل (panel) | اپ وبی که کارکنان کسب‌وکار با آن کار می‌کنند | مسیر <span dir="ltr">`/panel/*`</span> |
| صفحه‌ی آشپزخانه (kitchen screen) | صفحه‌ی زنده‌ی سفارش‌ها برای آشپزخانه و صندوق | <span dir="ltr">`/panel/kitchen`</span>، معمولاً روی تبلت |
| `qr_token` | مقدار تصادفی و یکتای هر میز که در QR چاپ می‌شود | جدول `dining_tables`؛ می‌شود از نو ساختش و آن‌وقت QR قبلی باطل است |
| `slug` | نام کوتاه و یکتای کسب‌وکار در نشانی | لینک عمومی منو <span dir="ltr">`/m/:slug`</span> برای اینستاگرام |
| درخواست خدمت (service request) | صدا زدن گارسون یا خواستن صورت‌حساب | نوع‌های `waiter` و `bill`؛ یکی در ۶۰ ثانیه برای هر میز و نوع |
| نشان (badge) | علامت کوچک روی آیتم | فقط `popular`، `new`، `chef` |
| برچسب رژیم و حساسیت‌زا | مقدارهای ثابت برای فیلتر منو | ستون‌های `diet_tags` و `allergens` با فهرست مجاز بخش ۷٫۲ مشخصات فنی |
| پیشنهاد همراه (pairing) | آیتمی که کنار آیتم دیگر پیشنهاد می‌شود | جدول `item_pairings`؛ اختیاری |
| منوی زمان‌دار | دسته‌ای که فقط در روزها و ساعت‌های مشخص دیده می‌شود | جدول `menu_schedules`؛ اختیاری |
| کلید «تمام شد» (sold-out) | بستن موقت یک آیتم | `is_available` و متد `SetItemAvailability`؛ هر سه نقش اجازه دارند |
| کد سفارش | شماره‌ی کوتاه سفارش برای صدا زدن مهمان | هر روز برای هر کسب‌وکار از نو شروع می‌شود؛ جدول `daily_counters` |
| پرداخت پای صندوق | پرداخت حضوری | سفارش از `pending` شروع می‌شود و صندوق‌دار با `MarkPaidAtCounter` علامت می‌زند |
| تسویه (settlement) | رسیدن پول پرداخت به حساب بانکی کسب‌وکار | مدل A یا B، تصمیم باز ۶؛ Tecso هرگز پول را نگه نمی‌دارد |
| دمو | کسب‌وکار نمایشی برای امتحان کردن | یک کافه و یک رستوران با `is_demo = true` روی `production` |
| انتشار ۱، ۲، ۳ (R1، R2، R3) | مرحله‌های عرضه‌ی محصول | محدوده‌ی انتشار ۱ در بخش ۲ مشخصات فنی |
| اختیاری (stretch) | کاری که اگر وقت کم بیاید اول به بعد می‌رود | گارسون هوشمند، ورود منو از عکس، داشبورد فروش، منوی زمان‌دار، پیشنهاد همراه |

## ۳. معماری

| واژه | معنی | در سرمیز |
|---|---|---|
| microservice | سرویس کوچکی که یک مسئولیت و داده‌ی خودش را دارد و جدا مستقر می‌شود | شش سرویس: `gateway`، `identity`، `catalog`، `order`، `realtime`، `ai` |
| gateway | تنها درِ ورودی عمومی API | سرویس `gateway`: REST به gRPC، بررسی توکن و نقش، محدودیت درخواست؛ بدون منطق کسب‌وکار |
| gRPC | روش فراخوانی هم‌زمان بین سرویس‌ها روی HTTP/2 | همه‌ی فراخوانی‌های سرویس به سرویس، با deadline پیش‌فرض ۲ ثانیه |
| Protobuf | زبان تعریف پیام‌ها و سرویس‌های gRPC | فایل‌ها در <span dir="ltr">`proto/sarmiz/<service>/v1/`</span> |
| فراخوانی هم‌زمان و ناهم‌زمان | منتظر جواب ماندن، در برابر فرستادن رویداد و ادامه دادن | هم‌زمان با gRPC فقط در گراف مجاز بخش ۴٫۱؛ ناهم‌زمان با NATS |
| event (رویداد) | پیامی که می‌گوید چیزی اتفاق افتاده | مثلاً `sarmiz.order.order.created`؛ فهرست کامل در بخش ۶٫۳ مشخصات فنی |
| NATS JetStream | سیستم پیام‌رسانی با ذخیره‌ی پیام‌ها | stream به نام `SARMIZ` |
| subject | نشانی یک رویداد در NATS | الگوی <span dir="ltr">`sarmiz.<service>.<entity>.<event>`</span> |
| envelope (پاکت رویداد) | قالب مشترکی که هر رویداد در آن پیچیده می‌شود | فیلدهای `id`، `type`، `version`، `time`، `venue_id`، `trace_id`، `data` |
| outbox | جدولی که رویداد در همان تراکنش تغییر داده در آن نوشته می‌شود و بعد منتشر می‌شود | جدول `outbox` در `catalog` و `orders`؛ متریک `outbox_lag_seconds` زیر ۶۰ |
| relay | حلقه‌ای که ردیف‌های outbox را منتشر و علامت «فرستاده شد» می‌زند | بخشی از شاسی مشترک (`W1-ORD-4`) |
| idempotency | اینکه تکرار یک کار نتیجه را دوباره عوض نکند | `Idempotency-Key` روی ساخت سفارش و پرداخت؛ مصرف‌کننده‌ها با `id` رویداد تکراری را کنار می‌گذارند |
| read model | نسخه‌ای از داده که برای خواندن سریع آماده شده | منوی عمومی در Redis با کلید <span dir="ltr">`menu:{venue_id}:{locale}:{menu_version}`</span> |
| saga | زنجیره‌ای از تراکنش‌ها در چند سرویس با جبران خطا | عمداً نداریم؛ برای همین `order` پرداخت را هم دارد |
| circuit breaker | کلیدی که بعد از خطاهای پشت‌سرهم، فراخوانی را موقتاً قطع می‌کند | دور همه‌ی کلاینت‌های gRPC و HTTP |
| WebSocket | اتصال دوطرفه‌ی ماندگار بین مرورگر و سرور | سرویس `realtime`، نشانی <span dir="ltr">`/ws`</span>؛ فقط کانال خبر |
| trusted metadata | اطلاعاتی که `gateway` همراه هر فراخوانی می‌فرستد | `x-request-id`، `x-user-id`، `x-venue-id`، `x-role`، `x-guest-session` |

| `protovalidate` | قاعده‌های اعتبارسنجی فیلد داخل proto | اعتبارسنجی در لبه و دوباره در سرویس |
| OpenAPI | قالب استاندارد توصیف REST API | `docs/api/openapi.yaml` از protoها ساخته می‌شود و کلاینت وب از آن |

| interceptor | تابعی که دور هر فراخوانی gRPC اجرا می‌شود | request id، recovery، لاگ، متریک و tracing در شاسی |
| handler، service، repository | سه لایه‌ی هر سرویس Go | ترجمه و اعتبارسنجی، قاعده‌های کسب‌وکار، SQL با pgx |
| pgx | کتابخانه‌ی PostgreSQL برای Go | همه‌ی SQL با پارامتر، هر متد `venue_id` می‌گیرد |
| deadline | سقف زمانی یک فراخوانی | پیش‌فرض ۲ ثانیه برای هر فراخوانی gRPC |
| cursor pagination | صفحه‌بندی با نشانگر به‌جای شماره‌ی صفحه | <span dir="ltr">`?limit=`</span> (پیش‌فرض ۲۰، حداکثر ۱۰۰) و <span dir="ltr">`?cursor=`</span>، جواب با `next_cursor` |
| قالب خطای یکسان | یک شکل JSON برای همه‌ی خطاها | `code`، `message`، `fields`، `request_id`؛ کدها در بخش ۶٫۱ مشخصات فنی |
| مصرف‌کننده‌ی idempotent | مصرف‌کننده‌ای که پیام تکراری را یک بار اعمال می‌کند | جدول `processed_events` |
| FastAPI | چارچوب وب Python | سرویس `ai` |
| Pydantic | کتابخانه‌ی اعتبارسنجی داده در Python | همه‌ی ورودی‌ها و خروجی‌های `ai`، از جمله خروجی مدل |
| `go.work` | فضای کاری Go برای چند ماژول | یک ماژول برای هر سرویس و یکی برای `libs/go/kit` |

## ۵. دیتابیس

| واژه | معنی | در سرمیز |
|---|---|---|
| database per service | هر سرویس دیتابیس و نقش جدای خودش را دارد | دیتابیس‌های `identity`، `catalog`، `orders`، `ai` روی یک سرور PostgreSQL |
| migration | فایلی که شکل دیتابیس را قدم‌به‌قدم عوض می‌کند | با goose، در <span dir="ltr">`services/<name>/migrations/`</span> |
| expand-then-contract | اول چیز تازه را اضافه کن، بعد از جابه‌جایی کد قدیمی را حذف کن | تا برگرداندن کد همیشه امن باشد |
| JSONB | ستون JSON دودویی در PostgreSQL | متن‌های چندزبانه مثل `name` با کلید زبان |
| snapshot | کپی داده در لحظه‌ی ثبت | نام، قیمت و گزینه‌ها در `order_items` تا ویرایش منو سفارش قدیمی را عوض نکند |
| state machine (ماشین حالت) | فهرست وضعیت‌ها و گذارهای مجاز بینشان | وضعیت سفارش و وضعیت پرداخت در بخش ۷٫۳ مشخصات فنی |
| UUID | شناسه‌ی ۱۲۸ بیتی یکتا | کلید همه‌ی جدول‌ها؛ ارجاع بین سرویس‌ها بدون foreign key |
| `menu_version` | شماره‌ای که با هر تغییر منو بالا می‌رود | در همان تراکنش تغییر؛ کلید کش و `ETag` از آن ساخته می‌شود |
| ریال `bigint` | پول به شکل عدد صحیح | ستون‌ها و فیلدهای `_rial`؛ رابط تومان نشان می‌دهد |
| row lock | قفل کردن یک ردیف تا تراکنش تمام شود | `HandleCallback` ردیف پرداخت را قفل می‌کند |
| connection pool | مجموعه‌ی اتصال‌های آماده به دیتابیس | pgx pool با شروع ۱۰ اتصال برای هر Pod |
| PgBouncer و read replica | واسط اتصال و نسخه‌ی فقط‌خواندنی دیتابیس | مسیر رشد، بعد از انتشار ۱ |

## ۶. امنیت

| واژه | معنی | در سرمیز |
|---|---|---|
| OTP | کد یک‌بارمصرف | ۶ رقم، ۱۲۰ ثانیه، حداکثر ۵ تلاش، hash‌شده در Redis |
| JWT | توکن امضاشده با claimهای کاربر | توکن دسترسی ۱۵ دقیقه‌ای با claimهای `sub`، `adm`، `mem` |
| Ed25519 | الگوریتم امضای دیجیتال | امضای JWTها در `identity` |
| JWKS | فهرست کلیدهای عمومی برای بررسی امضا | `identity` منتشر می‌کند و `gateway` ۱۰ دقیقه کش می‌کند |
| refresh token rotation | عوض کردن توکن تازه‌سازی در هر استفاده | ۳۰ روزه؛ استفاده‌ی دوباره از توکن قدیمی کل خانواده (`family_id`) را باطل می‌کند |
| کوکی `HttpOnly` | کوکی‌ای که JavaScript نمی‌تواند بخواندش | `sz_at` و `sz_rt` با `Secure` و `SameSite=Lax` |
| CSRF | فریب مرورگر برای فرستادن درخواست به نام کاربر | `SameSite=Lax` و بررسی Origin در `gateway` |
| CORS | قاعده‌ی مرورگر برای درخواست از دامنه‌ی دیگر | فقط دامنه‌های سرمیز مجازند |
| tenant isolation (جداسازی کسب‌وکارها) | داده‌ی یک مشتری به دیگری نرسد | فیلتر `venue_id` در هر query؛ کسب‌وکار دیگر `not_found` می‌گیرد؛ مجموعه‌ی <span dir="ltr">`tests/isolation/`</span> |
| permission matrix | جدول نقش‌ها و کارهای مجاز | سه نقش `owner`، `manager`، `staff` در بخش ۸ مشخصات فنی |
| stream ticket | JWT کوتاه‌عمر برای باز کردن WebSocket | ۶۰ ثانیه، با scope <span dir="ltr">`venue:<id>`</span> یا <span dir="ltr">`order:<id>`</span> |
| `order_token` | کلید خواندن یک سفارش برای مهمان | ۱۲۸ بیت تصادفی، فقط یک بار برمی‌گردد، hash‌شده ذخیره می‌شود |
| rate limiting | محدود کردن تعداد درخواست | در `gateway` با Redis؛ جواب `429` و `Retry-After` |
| sliding window | شمارش درخواست‌ها در پنجره‌ی زمانی لغزان | الگوریتم محدودیت درخواست در بخش ۱۰ مشخصات فنی |
| audit log | ثبت کارهای حساس | ورود، تغییر عضویت، تنظیمات پرداخت، وضعیت کسب‌وکار |
| AES-256-GCM | رمزنگاری متقارن با بررسی سلامت داده | اطلاعات درگاه هر کسب‌وکار در `payment_configs` |
| NetworkPolicy | قاعده‌ی شبکه بین Podها | فقط `gateway` و `realtime` از بیرون در دسترس‌اند |
| CSP | هدری که می‌گوید صفحه از کجا اسکریپت بگیرد | از ingress و وب‌سرور، همراه HSTS و `nosniff` |
| XSS | اجرای اسکریپت مهاجم در صفحه | متن منو و جواب مدل همیشه متن ساده‌اند، هرگز HTML |
| secret | کلید، رمز یا توکن | فقط در Kubernetes secret و GitHub secret؛ اسکن با gitleaks |

## ۸. زیرساخت

| واژه | معنی | در سرمیز |
|---|---|---|

| Helm | ابزار بسته‌بندی و استقرار روی Kubernetes | یک chart عمومی برای سرویس‌های Go؛ برگشت با `helm rollback` |
| namespace | بخش جدا در یک کلاستر | `staging` و `production` |
| ingress و cert-manager | ورودی HTTP کلاستر و صدور خودکار گواهی TLS | فقط `gateway` و `realtime` پشت ingress |
| HPA | مقیاس خودکار تعداد Podها | روی CPU با هدف ۷۰ درصد |
| liveness و readiness | «زنده‌ای؟» و «آماده‌ی کاری؟» | <span dir="ltr">`/healthz`</span> و <span dir="ltr">`/readyz`</span> در هر سرویس |
| CDN | شبکه‌ی کش نزدیک کاربر | عکس‌ها و فایل‌های اپ، از ارائه‌دهنده‌ی ایرانی |
| ETag | شناسه‌ی نسخه‌ی یک پاسخ HTTP | منوی عمومی، ساخته‌شده از `menu_version` و زبان |
| object storage | ذخیره‌ی فایل سازگار با S3 | باکت‌های `sarmiz-media` و `sarmiz-imports`؛ MinIO در `local` |
| staging | محیط آزمایشی شبیه production | استقرار خودکار با هر merge، درگاه sandbox |
| structured log | لاگ به شکل JSON با فیلدهای ثابت | `slog` و `structlog`، جمع‌آوری در Loki |
| trace | مسیر یک درخواست از میان سرویس‌ها | OpenTelemetry به Tempo، حتی داخل پاکت رویداد |
| RED metrics | نرخ، خطا و مدت هر متد | از <span dir="ltr">`/metrics`</span> هر سرویس در Prometheus |
| Grafana و Alertmanager | داشبورد و ارسال هشدار | هشدارها به گروه Bale یا Telegram تیم |
| GlitchTip | ردیاب خطای خودمیزبان سازگار با Sentry | Go، Python و وب؛ release برابر git SHA |
| RPO | حداکثر داده‌ای که ممکن است از دست برود | ۲۴ ساعت در انتشار ۱ (پشتیبان شبانه) |
| RTO | حداکثر زمان برگشت سرویس | ۴ ساعت |
