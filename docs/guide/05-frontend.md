# فرانت‌اند

این فصل به این سؤال جواب می‌دهد: اپ وب سرمیز چطور ساخته می‌شود تا برای مهمان سریع، برای آشپزخانه قابل اعتماد و برای تیم قابل نگه‌داری باشد؟

[بازگشت به فهرست مستندات](../README.md)

## ۱. چرا مهم است

همه‌ی کاربران سرمیز فقط اپ وب را می‌بینند: مهمان روی گوشی و اینترنت ضعیف، آشپزخانه روی تبلتی که ساعت‌ها روشن می‌ماند، و صاحب کسب‌وکار در پنل. اگر منوی مهمان کند باز شود، مهمان از گارسون منوی کاغذی می‌خواهد؛ اگر صفحه‌ی آشپزخانه بعد از قطع اینترنت سفارشی را نشان ندهد، غذایی درست نمی‌شود. این فصل بخش ۱۹ [مشخصات فنی](../SPEC.md) را باز می‌کند و هر جا مشخصات فنی چیزی را تصمیم نگرفته، آن را «پیشنهاد اولیه» نوشته‌ایم.

## ۲. تصمیم‌ها در یک نگاه

| موضوع | تصمیم | چرا |
|---|---|---|
| ساختار | یک اپ Vite (React، TypeScript strict) با چهار گروه مسیرِ lazy | یک build و یک استقرار، و کد پنل به گوشی مهمان نمی‌رسد |
| وضعیت سرور | TanStack Query با `staleTime` جدا برای هر منبع | کش، تلاش دوباره و هم‌زمانی را یک کتابخانه‌ی آشنا انجام می‌دهد |
| کلاینت API | نوع‌ها از `docs/api/openapi.yaml` ساخته می‌شوند؛ `any` ممنوع | قرارداد و کد از هم جدا نمی‌شوند |
| ورود | کوکی‌های `HttpOnly` به نام `sz_at` و `sz_rt` | JavaScript هیچ‌وقت توکن را نمی‌بیند |
| استایل | Tailwind فقط با utilityهای منطقی (<span dir="ltr">`ms-`</span>، <span dir="ltr">`me-`</span>، <span dir="ltr">`ps-`</span>، <span dir="ltr">`pe-`</span>، `text-start`) | رابط اول راست‌به‌چپ است و انگلیسی هم درست می‌ماند |
| سبد مهمان | در `localStorage` با کلید میز | مهمان حساب ندارد و سبد با تازه کردن صفحه نمی‌پرد |
| زمان واقعی | WebSocket فقط خبر می‌دهد؛ وضعیت واقعی از REST می‌آید | رویداد گم‌شده نباید سفارش را گم کند |

## ۳. یک اپ، چهار گروه مسیر

| مسیر | مخاطب | نکته‌ی فنی |
|---|---|---|
| <span dir="ltr">`/`</span> و <span dir="ltr">`/pricing`</span> | بازدیدکننده | هنگام build از پیش به HTML ساخته می‌شود (prerender) تا موتور جست‌وجو بخواندش |
| <span dir="ltr">`/t/:qrToken`</span>، <span dir="ltr">`/m/:slug`</span>، <span dir="ltr">`/o/:orderId`</span> | مهمان | سخت‌ترین بودجه‌ی کارایی؛ بدون ورود |
| <span dir="ltr">`/panel/*`</span> و <span dir="ltr">`/panel/kitchen`</span> | صاحب کسب‌وکار و آشپزخانه | ورود لازم است |
| <span dir="ltr">`/admin/*`</span> | ادمین Tecso | ورود با claim به نام `adm` |

هر گروه با `React.lazy` و `Suspense` یک chunk جداست (تکه‌ای از JavaScript که فقط وقتی لازم شد دانلود می‌شود) و تا رسیدنش یک skeleton نشان داده می‌شود.

مسیر دقیق زیرصفحه‌های پنل (مثلاً صفحه‌ی ورود یا ویرایشگر منو) در مشخصات فنی نیامده است. بخش فرانت آن‌ها را در `W1-WEB-1` و wireframeهای `W1-WEB-3` تعیین می‌کند و در [README اپ وب](../../web/README.md) می‌نویسد.

## ۵. وضعیت سرور و وضعیت محلی

- **TanStack Query** برای هر چیزی که مرجعش سرور است: منو، سفارش‌ها، `GET /me`، تنظیمات. آن را در state محلی کپی نکن، وگرنه دو نسخه داری که از هم جدا می‌شوند.
- **`useState`** برای وضعیتی که فقط همین صفحه لازم دارد، مثل باز بودن sheet. **`localStorage`** فقط برای سبد مهمان و `guest_session_id`. توکن و کد یک‌بارمصرف هیچ‌جای مرورگر ذخیره نمی‌شوند.

**کلید query همیشه شناسه‌ی کسب‌وکار را دارد.** اگر صاحب کسب‌وکار بین دو کسب‌وکار جابه‌جا شود، کش یکی هیچ‌وقت در صفحه‌ی دیگری دیده نمی‌شود. همه‌ی کلیدها را از یک فایل بساز:

</div>

```ts
export const qk = {
  me: ["me"] as const,
  venue: (venueId: string) => ["venue", venueId] as const,
  menu: (venueId: string) => ["venue", venueId, "menu"] as const,
  orders: (venueId: string, f: OrderFilter) => ["venue", venueId, "orders", f] as const,
  publicMenu: (qrToken: string, locale: string) => ["public-menu", qrToken, locale] as const,
  guestOrder: (orderId: string) => ["guest-order", orderId] as const,
};
```

<div dir="rtl">

`staleTime` برای هر منبع (پیشنهاد اولیه؛ بعد از اندازه‌گیری تنظیم کن):

| منبع | `staleTime` | دلیل |
|---|---|---|
| منوی عمومی | ۳۰ ثانیه | با `max-age=30` پاسخ HTTP می‌خواند؛ قیمت نهایی را `PriceItems` حساب می‌کند |
| `GET /me` | ۵ دقیقه | بعد از ساخت کسب‌وکار دستی invalidate می‌شود |
| منو و تنظیمات در پنل | ۰ | صاحب کسب‌وکار باید آخرین نسخه را ویرایش کند |
| سفارش‌ها در پنل و صفحه‌ی آشپزخانه | ۰، با `refetchInterval` برابر ۳۰ ثانیه | WebSocket خبر می‌دهد؛ ۳۰ ثانیه تور ایمنی بخش ۶٫۴ مشخصات فنی است |
| سفارش مهمان | ۰ | با رویداد <span dir="ltr">`order:<order_id>`</span> تازه می‌شود |

**به‌روزرسانی خوش‌بینانه برای کلید «تمام شد».** کارمند آشپزخانه نباید برای یک لمس منتظر شبکه بماند. اول رابط را عوض کن، اگر سرور رد کرد برگردان:

</div>

```ts
useMutation({
  mutationFn: (v: { itemId: string; available: boolean }) => api.setItemAvailability(venueId, v),
  onMutate: async (v) => {
    await qc.cancelQueries({ queryKey: qk.menu(venueId) });
    const prev = qc.getQueryData<Menu>(qk.menu(venueId));
    qc.setQueryData<Menu>(qk.menu(venueId), (m) => m && setAvailable(m, v.itemId, v.available));
    return { prev };
  },
  onError: (_e, _v, ctx) => { qc.setQueryData(qk.menu(venueId), ctx?.prev); toast.error(t("kitchen.soldOutFailed")); },
  onSettled: () => qc.invalidateQueries({ queryKey: qk.menu(venueId) }),
});
```

به‌روزرسانی خوش‌بینانه فقط برای کارهای کوچک و برگشت‌پذیر است. ثبت سفارش، پرداخت و «پرداخت‌شده پای صندوق» هرگز خوش‌بینانه نیستند.

## ۶. کلاینت API تایپ‌شده و الگوی خطا

نوع‌ها از `docs/api/openapi.yaml` ساخته می‌شوند و این فایل خودش از protoها ساخته می‌شود (`W1-PA-3`). ابزار ساخت کلاینت در مشخصات فنی نیامده؛ بخش فرانت در `W1-WEB-5` انتخاب می‌کند و دستورش را در [README اپ وب](../../web/README.md) می‌نویسد. پوشه‌ی <span dir="ltr">`api/generated/`</span> دستی ویرایش نمی‌شود؛ اگر نوعی اشتباه است، proto را درست کن. شرح قراردادها در [فصل ۶](06-api-and-contracts.md) است.

همه‌ی خطاها یک شکل دارند: <span dir="ltr">`{"error": {"code", "message", "fields", "request_id"}}`</span>. یک تابع آن را به یک کلاس تبدیل می‌کند و بقیه‌ی کد فقط با `code` کار می‌کند:

</div>

```ts
async function toApiError(res: Response): Promise<ApiError> {
  const body = (await res.json().catch(() => null)) as ErrorBody | null;
  const retry = res.headers.get("Retry-After");
  return new ApiError(res.status, body?.error.code ?? "internal", body?.error.fields ?? {},
    body?.error.request_id ?? "", retry ? Number(retry) : undefined);
}
```

<div dir="rtl">

| کد | رابط چه کار می‌کند |
|---|---|
| `validation_failed` | `fields` را کنار همان ورودی‌های فرم نشان بده |
| `unauthenticated` | یک بار `POST /api/v1/auth/refresh`، بعد همان درخواست را یک بار تکرار کن؛ اگر باز ۴۰۱ بود، به صفحه‌ی ورود برو |
| `permission_denied` | پیام «این کار با نقش تو ممکن نیست»؛ تلاش دوباره نکن |
| `not_found` | صفحه‌ی «پیدا نشد»؛ برای QR نامعتبر: «این QR دیگر کار نمی‌کند، از گارسون بپرس» |
| `conflict` و `failed_precondition` | پیام روشن از متن i18n همان کد، مثلاً «این آیتم الان تمام شده» |
| `rate_limited` | ثانیه‌های `Retry-After` را بخوان، دکمه را تا آن موقع غیرفعال کن و شمارش معکوس نشان بده |
| `unavailable` و `internal` | «الان نشد، دوباره امتحان کن» و گزارش به GlitchTip |

`message` سرور برای برنامه‌نویس است و به انگلیسی؛ آن را مستقیم به کاربر نشان نده. متن کاربر از لایه‌ی i18n و با لحن [راهنمای برند](../brand/README.md) می‌آید. پیشنهاد اولیه: `request_id` را با عنوان «کد پیگیری» کوچک زیر پیام خطا نشان بده تا پشتیبانی بتواند آن را در لاگ‌ها پیدا کند.

برای `POST .../orders` و `POST .../pay` هنگام کلیک یک `Idempotency-Key` با <span dir="ltr">`crypto.randomUUID()`</span> بساز و در هر تلاش دوباره‌ی **همان** کلیک، همان کلید را بفرست. کلید تازه در هر تلاش، سفارش دوم می‌سازد.

## ۷. ورود در مرورگر

| قاعده | جزئیات |
|---|---|
| توکن کجاست | در کوکی‌های `sz_at` (۱۵ دقیقه) و `sz_rt` (۳۰ روز)، هر دو `HttpOnly`، `Secure` و `SameSite=Lax`. کوکی `sz_rt` فقط به <span dir="ltr">`/api/v1/auth`</span> فرستاده می‌شود |
| JavaScript چه می‌بیند | هیچ توکنی. هویت و نقش‌ها از `GET /api/v1/me` می‌آید |
| درخواست‌ها و CSRF | با <span dir="ltr">`credentials: "include"`</span> تا کوکی همراهشان برود؛ `gateway` هدر Origin را بررسی می‌کند، پس اپ فقط از دامنه‌ی خود سرمیز درخواست می‌فرستد |
| مسیر محافظت‌شده | کامپوننت guard که `GET /me` را می‌خواند؛ در حال بارگذاری skeleton، با ۴۰۱ رفتن به صفحه‌ی ورود با نشانی برگشت |
| نقش‌ها در رابط | دکمه‌هایی که نقش اجازه نمی‌دهد پنهان می‌شوند، ولی تصمیم واقعی با `gateway` و سرویس‌هاست |
| خروج | `POST /api/v1/auth/logout` و بعد <span dir="ltr">`queryClient.clear()`</span> |

**تازه‌سازی تک‌پرواز.** اگر پنج درخواست هم‌زمان ۴۰۱ بگیرند، فقط یک `POST /auth/refresh` فرستاده می‌شود و بقیه منتظر همان می‌مانند. اگر هر کدام جدا تازه‌سازی کنند، توکن تازه‌سازی چند بار استفاده می‌شود و `identity` آن را استفاده‌ی دوباره می‌بیند و کل خانواده را باطل می‌کند.

**بعد از ساخت کسب‌وکار.** نقش‌ها از claim به نام `mem` در توکن خوانده می‌شوند و توکن فعلی هنوز نقش تازه را ندارد. پس بعد از موفقیت `POST /api/v1/venues`، اول `POST /api/v1/auth/refresh` را صدا بزن، بعد `qk.me` را invalidate کن و بعد به پنل همان کسب‌وکار برو. اینکه `GET /me` پرچم ادمین را هم برمی‌گرداند یا نه، در قرارداد proto بخش هسته (`W1-CORE-4`) روشن می‌شود؛ guard مسیر <span dir="ltr">`/admin/*`</span> به آن وابسته است. جزئیات بیشتر در [فصل ۹](09-auth-and-permissions.md).

## ۸. مسیر مهمان

- **بدون ورود.** هیچ صفحه‌ی مهمان کوکی ورود نمی‌خواهد و به <span dir="ltr">`/auth/*`</span> درخواست نمی‌دهد.
- **`guest_session_id`.** بار اول یک مقدار تصادفی با <span dir="ltr">`crypto.randomUUID()`</span> بساز، در `localStorage` نگه دار و در هدر `X-Guest-Session` همه‌ی درخواست‌های عمومی بفرست. برای محدودیت درخواست و «سفارش‌های من روی این دستگاه» به کار می‌رود.
- **سبد.** در `localStorage` با کلید میز، مثلاً <span dir="ltr">`cart:<qrToken>`</span> (پیشنهاد اولیه برای نام کلید). سبد فقط شناسه‌ی آیتم، شناسه‌ی گزینه‌ها، تعداد و یادداشت را نگه می‌دارد. قیمتی که در سبد نشان می‌دهی از منوی فعلی حساب می‌شود و فقط برای نمایش است؛ جمع را سرور حساب می‌کند. بعد از ثبت موفق سفارش، سبد همان میز را خالی کن.
- **`order_token`.** فقط یک بار در جواب ساخت سفارش می‌آید و بدون آن سفارش خوانده نمی‌شود. آن را برای همان سفارش در `localStorage` نگه دار تا <span dir="ltr">`/o/:orderId`</span> بعد از تازه کردن صفحه هم کار کند. اینکه توکن در هدر فرستاده شود یا جای دیگر، در قرارداد `W1-ORD-2` تعیین می‌شود.
- **<span dir="ltr">`/m/:slug`</span>** فقط منو را نشان می‌دهد؛ چون `qr_token` ندارد، دکمه‌ی سفارش ندارد.

**بودجه‌ی کارایی** (بخش ۳ مشخصات فنی): روی شبکه‌ی 4G، Largest Contentful Paint (زمان نمایش بزرگ‌ترین بخش صفحه) زیر ۲ ثانیه، و JavaScript مسیر مهمان حداکثر ۱۵۰ کیلوبایت فشرده با gzip.

| راه رسیدن به بودجه | چه کار کن |
|---|---|
| مسیرهای lazy | مهمان فقط chunk گروه مهمان را دانلود می‌کند. کتابخانه‌ی نمودار، drag and drop و ویرایشگرهای پنل وارد این chunk نشوند |
| عکس در سه عرض | عکس‌ها در عرض‌های ۳۲۰، ۸۰۰ و ۱۶۰۰ با کلید `v/{venue_id}/{sha256}-{width}.webp` وجود دارند. با `srcset` و `sizes` بگذار مرورگر کوچک‌ترین مناسب را بردارد؛ `width` و `height` بده تا صفحه نپرد |
| skeleton | به‌جای spinner، شکل خاکستری کارت‌ها را فوری نشان بده |
| فونت | وزیرمتن همراه اپ و با `font-display: swap`، نه از سرویس بیرونی |
| اندازه‌گیری | اندازه‌ی chunk مهمان را در CI بسنج و با Lighthouse روی پروفایل 4G کند امتحان کن (ابزار دقیق: پیشنهاد اولیه، با تصمیم تیم) |

</div>

```tsx
<img src={imageUrl(item, 320)} width={320} height={240} loading="lazy" alt={pickText(item.name, locale)}
  srcSet={[320, 800, 1600].map((w) => `${imageUrl(item, w)} ${w}w`).join(", ")}
  sizes="(min-width: 768px) 33vw, 100vw" />
```

## ۹. صفحه‌ی آشپزخانه

<span dir="ltr">`/panel/kitchen`</span> تنها صفحه‌ای است که ساعت‌ها بدون دست زدن باز می‌ماند. قاعده‌اش از بخش‌های ۶٫۴ و ۱۶ مشخصات فنی:

1. هنگام باز شدن، سفارش‌ها را از `GET /api/v1/venues/{venue_id}/orders` بگیر.
2. با `POST /api/v1/stream-tickets` یک ticket با scope <span dir="ltr">`venue:<venue_id>`</span> بگیر. ticket یک JWT با عمر ۶۰ ثانیه است، پس برای **هر** اتصال دوباره ticket تازه بگیر.
3. به <span dir="ltr">`wss://<host>/ws?ticket=<ticket>`</span> وصل شو. با هر رویداد، query سفارش‌ها را invalidate کن یا سفارش را در کش به‌روز کن؛ رویداد تکراری را با `id` پاکت رویداد کنار بگذار.
4. با هر اتصال و هر اتصال دوباره، فهرست سفارش‌ها را دوباره بخوان. جدا از آن، هر ۳۰ ثانیه هم بخوان.
5. اگر اتصال قطع شد، با backoff (فاصله‌ی رو به افزایش) و کمی تصادف دوباره وصل شو. پیشنهاد اولیه: ۱، ۲، ۴، ۸ تا سقف ۳۰ ثانیه.
6. تا وقتی `realtime` در دسترس نیست، هر ۵ ثانیه سفارش‌ها را بخوان و نشانگر «اتصال زنده قطع است» را نشان بده.

| موضوع | قاعده |
|---|---|
| صدا | مرورگر بدون لمس کاربر صدا پخش نمی‌کند. شروع کار با دکمه‌ی «شروع شیفت» باشد تا صدا آزاد شود. با `order.created` و درخواست خدمت تازه صدا پخش کن |
| چیدمان تبلت | افقی، ستون‌ها بر اساس وضعیت (`pending`، `accepted`، `preparing`، `ready`)، دکمه‌های بزرگ برای جلو بردن وضعیت، کد سفارش و نام میز درشت؛ پیشنهاد اولیه: Screen Wake Lock API برای روشن ماندن صفحه |
| سفارش پرداخت‌نشده | سرور سفارش `awaiting_payment` را نمی‌فرستد؛ رابط هم آن را فیلتر کند |
| کلید «تمام شد» | روی همین صفحه، با به‌روزرسانی خوش‌بینانه‌ی بخش ۵ (`W4-WEB-2`) |

## ۱۰. توکن‌های طراحی و کامپوننت‌های پایه

رنگ‌ها و فونت از [راهنمای برند](../brand/README.md) می‌آیند و فقط یک بار، در `styles/tokens.css` به شکل متغیر CSS، تعریف می‌شوند: کرم <span dir="ltr">`#FBF6EC`</span>، اسپرسو <span dir="ltr">`#2B1D14`</span>، زعفرانی <span dir="ltr">`#E8A013`</span> و فونت وزیرمتن. پیکربندی Tailwind فقط به همین متغیرها اشاره می‌کند.

> [!IMPORTANT]
> متن زعفرانی روی زمینه‌ی کرم ممنوع است (نسبت تضاد حدود ۲ به ۱). روی دکمه‌ی زعفرانی متن اسپرسو بگذار.

در منوی مهمان، <span dir="ltr">`--venue-theme`</span> از `theme_color` همان کسب‌وکار پر می‌شود و هویت کسب‌وکار جلوتر از سرمیز است. انتخاب رنگ متن خوانا روی آن در [فصل ۲۲](22-i18n-rtl-accessibility.md) آمده است.

کامپوننت‌های پایه‌ی `W1-WEB-2`: `Button`، `Input`، `Card`، `Sheet`/`Modal`، `Toast`، `Skeleton` و `EmptyState`. هر کدام از روز اول حالت focus دیدنی، کار با صفحه‌کلید، ناحیه‌ی لمس دست‌کم ۴۴ پیکسل و نسخه‌ی راست‌به‌چپ دارند. صفحه‌ها رنگ و فاصله را مستقیم ننویسند؛ از همین کامپوننت‌ها و توکن‌ها استفاده کنند.

## ۱۱. فرم‌ها و اعتبارسنجی

- اعتبارسنجی مرورگر فقط برای تجربه‌ی بهتر است. مرجع، `protovalidate` در `gateway` و قاعده‌های سرویس است. خطای `validation_failed` را با `fields` به ورودی‌ها وصل کن. هر ورودی `label` دارد و دکمه‌ی ثبت تا رسیدن جواب غیرفعال است.
- کتابخانه‌ی فرم در مشخصات فنی نیامده؛ بخش فرانت در هفته‌ی ۱ یکی انتخاب می‌کند و همه‌ی فرم‌ها از همان استفاده می‌کنند.
- فیلدهای چندزبانه (`name`، `description`) با تب زبان: فقط زبان‌های `enabled_locales`، و تب `fa` اجباری.
- قیمت را به تومان بگیر و هنگام فرستادن به عدد صحیح ریال تبدیل کن (ضرب در ۱۰). همه‌ی تبدیل‌ها در `lib/money.ts`، هیچ‌جا اعشار.
- شماره‌ی موبایل ممکن است با رقم فارسی تایپ شود. رقم‌ها را به لاتین برگردان و به قالب E.164 (<span dir="ltr">`+98...`</span>) بفرست.

## ۱۲. حالت‌های بارگذاری، خالی و خطا

هیچ صفحه‌ای صفحه‌ی سفید نشان نمی‌دهد. متن‌های ستون‌ها پیشنهاد اولیه‌اند و متن نهایی در wireframeها نوشته می‌شود.

| صفحه | بارگذاری | خالی | خطا |
|---|---|---|---|
| منوی مهمان | skeleton کارت‌ها | «این منو هنوز آیتمی ندارد» | QR نامعتبر: «از گارسون بپرس»؛ قطع شبکه: «دوباره امتحان کن» |
| برگه‌ی آیتم و سبد | دکمه‌ی در حال ثبت | «سبدت خالی است» و برگشت به منو | آیتم تمام‌شده: کنار همان آیتم در سبد |
| وضعیت سفارش | skeleton خط وضعیت | ندارد | «اتصال قطع شد، وضعیت را دوباره می‌گیریم» |
| ویرایشگر منو | skeleton فهرست | «اولین دسته‌ات را بساز» یا ورود از عکس | خطای فیلدها کنار ورودی‌ها |
| فهرست سفارش‌ها و ادمین | skeleton جدول | «امروز هنوز سفارشی نیامده» | پیام و دکمه‌ی تلاش دوباره |
| ورود | دکمه‌ی غیرفعال | ندارد | کد اشتباه کنار ورودی؛ `rate_limited` با شمارش معکوس |
| صفحه‌ی آشپزخانه | skeleton ستون‌ها | ستون‌های خالی با «منتظر سفارش» | نشانگر قطع اتصال و polling |

وقتی سرویس `ai` پایین است، دکمه‌های ترجمه و ورود منو پیام «الان نشد، کمی بعد دوباره امتحان کن» نشان می‌دهند و بقیه‌ی پنل کار می‌کند (بخش ۱۶ مشخصات فنی).

## ۱۳. error boundary و GlitchTip

- برای هر گروه مسیر یک error boundary بگذار تا خطای پنل منوی مهمان را خراب نکند. صفحه‌ی جایگزین با لحن برند و دکمه‌ی «دوباره امتحان کن».
- خطا با SDK مرورگر Sentry به GlitchTip خودمیزبان فرستاده می‌شود. `release` برابر git SHA است و source map (نقشه‌ی کد فشرده به کد اصلی) هنگام build بارگذاری می‌شود تا stack trace خوانا باشد.
- قبل از فرستادن، شماره‌ی موبایل، کد یک‌بارمصرف، `order_token` و نشانی‌هایی که `qr_token` دارند را پاک یا پوشیده کن. `W1-WEB-5` فقط جای این hook را می‌سازد؛ اتصال واقعی در `W2-PA-3` است. جزئیات در [فصل ۱۵](15-logs-and-error-tracking.md).

## ۱۴. صفحه‌ی معرفی از پیش ساخته‌شده

<span dir="ltr">`/`</span> و <span dir="ltr">`/pricing`</span> هنگام build به فایل HTML کامل تبدیل می‌شوند تا موتور جست‌وجو بدون اجرای JavaScript محتوا را ببیند (`W5-WEB-1`). ابزار prerender در مشخصات فنی نیامده و بخش فرانت در هفته‌ی ۵ انتخاب می‌کند. قاعده‌ها: `lang` و `dir` درست روی <span dir="ltr">`<html>`</span>، عنوان و توضیح برای هر صفحه، و ورودی «امتحان کن» به دو دمو. صفحه‌ی معرفی کد پنل را بارگذاری نمی‌کند. Nginx فایل‌ها را می‌دهد: فایل‌های با نام hash‌دار برای همیشه کش می‌شوند و `index.html` کش نمی‌شود. فقط قابلیتی را وعده بده که واقعاً ساخته شده است.

## ۱۵. تست به‌طور خلاصه

منطق خالص (تبدیل ریال به تومان، جمع نمایشی سبد، تبدیل خطا به `ApiError`، فاصله‌های backoff) با Vitest؛ کامپوننت‌ها با Testing Library و از دید کاربر؛ سه مسیر بخش ۱۳ مشخصات فنی با Playwright در `W5-WEB-5`. جزئیات در [فصل ۱۷](17-testing.md).

## چک‌لیست انتشار ۱

- [ ] chunk مسیر مهمان حداکثر ۱۵۰ کیلوبایت gzip است و LCP منوی دمو روی 4G کند زیر ۲ ثانیه اندازه‌گیری شده.
- [ ] هیچ `any` و نوع API دست‌نویسی در کد نیست، و هیچ توکنی در `localStorage`، `sessionStorage` یا state اپ نیست.
- [ ] بعد از ساخت کسب‌وکار، بدون خروج و ورود دوباره، پنل همان کسب‌وکار باز می‌شود.
- [ ] صفحه‌ی آشپزخانه بعد از قطع و وصل Wi-Fi همه‌ی سفارش‌های آن فاصله را نشان می‌دهد و با خاموش شدن `realtime` در `staging` هر ۵ ثانیه تازه می‌شود.
- [ ] دو بار زدن دکمه‌ی ثبت سفارش فقط یک سفارش می‌سازد.
- [ ] هر صفحه‌ی جدول بخش ۱۲ حالت بارگذاری، خالی و خطا دارد.
- [ ] خطای عمدی در مرورگر با stack trace خوانا در GlitchTip دیده می‌شود و داده‌ی شخصی ندارد.
- [ ] هیچ <span dir="ltr">`ml-`</span>، <span dir="ltr">`mr-`</span>، <span dir="ltr">`pl-`</span>، <span dir="ltr">`pr-`</span>، <span dir="ltr">`left-`</span> یا `text-left` در کد نیست.
