# پشتیبان‌گیری و بازیابی

این فصل به یک سؤال جواب می‌دهد: اگر سرور، دیتابیس یا یک راز از دست برود، چه چیزی را از کجا برمی‌گردانی، چقدر داده از دست می‌رود و چقدر طول می‌کشد؟

[بازگشت به فهرست مستندات](../README.md)

## ۱. چرا مهم است

سرمیز در انتشار ۱ روی یک سرور است و همه‌ی دیتابیس‌ها روی یک دیسک‌اند ([فصل ۱۳](13-hosting-and-cloud.md)). یک دیسک خراب، یک migration بد یا یک `DELETE` بدون `WHERE` می‌تواند منوی پنجاه کسب‌وکار و سابقه‌ی سفارش و پرداختشان را ببرد. پشتیبانی که هیچ‌وقت بازیابی نشده، فقط یک امید است؛ برای همین در سرمیز هم پشتیبان شبانه کار است (`W4-PA-1`) و هم تمرین بازیابی (`W5-PA-2`).

## ۲. تصمیم‌ها در یک نگاه

| موضوع | تصمیم | چرا |
|---|---|---|
| RPO | ۲۴ ساعت در انتشار ۱ | پشتیبان شبانه؛ ساده و قابل فهم برای یک تیم کوچک |
| RTO | ۴ ساعت | کافه‌ها در این مدت با منوی کاغذی و صندوق کار می‌کنند؛ بیشتر از آن به اعتماد ضربه می‌زند |
| چه چیزی | هر چهار دیتابیس `identity`، `catalog`، `orders` و `ai`، شبانه و جدا | هر سرویس دیتابیس خودش را دارد و جدا برمی‌گردد |
| کجا | object storage، بیرون از سرور | با رفتن سرور، پشتیبان نباید برود |
| محافظت | رمز شده، با مدت نگه‌داری مشخص | پشتیبان همه‌ی داده‌ها را دارد؛ باید مثل خود داده محافظت شود |
| هشدار | «Backup: nightly job failed» | شکست بی‌صدا یعنی RPO واقعی چند روز است، نه ۲۴ ساعت |
| Redis | پشتیبان ندارد | هر چیزی در آن یا دوباره ساخته می‌شود یا کاربر دوباره درخواست می‌دهد |
| تمرین | بازیابی کامل از پشتیبان شبانه و یک runbook کامل (`W5-PA-2`) | تنها راه دانستن اینکه پشتیبان کار می‌کند |

## ۳. RPO و RTO به زبان ساده

- **RPO (Recovery Point Objective):** حداکثر داده‌ای که حاضریم از دست بدهیم، به زمان. RPO برابر ۲۴ ساعت یعنی اگر ساعت ۱۸ سرور برود و آخرین پشتیبان مال ۰۳ بامداد باشد، سفارش‌ها، تغییرات منو و ثبت‌نام‌های این ۱۵ ساعت از دست رفته‌اند.
- **RTO (Recovery Time Objective):** حداکثر زمانی که سرمیز بعد از فاجعه از کار افتاده است، تا وقتی دوباره منو باز شود و سفارش ثبت شود. ۴ ساعت یعنی ساختن سرور تازه، استقرار، بازیابی دیتابیس‌ها و عوض کردن DNS باید در ۴ ساعت جا شود.

> [!IMPORTANT]
> RTO فقط وقتی واقعی است که یک بار زمانش را اندازه گرفته باشی. اگر تمرین بازیابی ۶ ساعت طول کشید، RTO تو ۶ ساعت است، هر چه هم در مشخصات فنی نوشته باشد. یا روش را سریع‌تر کن یا موضوع را به منتور بگو.

## ۴. چه چیزی پشتیبان می‌خواهد و چه چیزی نه

| چیز | پشتیبان؟ | چرا و چطور |
|---|---|---|
| دیتابیس `identity` | بله، شبانه | کاربران، نقش‌ها، `audit_log` |
| دیتابیس `catalog` | بله، شبانه | کسب‌وکارها، میزها و `qr_token`ها (QRهای چاپ‌شده به آن‌ها وابسته‌اند)، منو، ترجمه‌ها |
| دیتابیس `orders` | بله، شبانه | سفارش‌ها، پرداخت‌ها، اطلاعات درگاه رمزشده |
| دیتابیس `ai` | بله، شبانه | `menu_chunks`؛ از روی منو دوباره ساختنی است، ولی بازسازی کامل با مدل وقت‌گیر است |
| bucket `sarmiz-media` | بیرون از سرور است و با رفتن سرور نمی‌رود؛ خطرش پاک شدن اشتباهی است | روشش (نسخه‌بندی bucket اگر ارائه‌دهنده دارد، یا کپی دوره‌ای) با `W4-PA-1` |
| bucket `sarmiz-imports` | نه | فایل موقت است و بعد از ۳۰ روز خودش پاک می‌شود |
| رازها | بله، یک نسخه‌ی امن بیرون از cluster | بدون کلید AES، ستون `credentials_enc` بعد از بازیابی بی‌مصرف است |
| پیکربندی cluster | در Git، پوشه‌ی <span dir="ltr">`deploy/`</span> | chartها، valueها، داشبوردها و هشدارها از Git دوباره ساخته می‌شوند |
| Redis | نه | جدول پایین |
| NATS JetStream | نه (پیشنهاد اولیه؛ مشخصات فنی چیزی نگفته) | بخش ۸ |

اگر Redis خالی شود چه از دست می‌رود:

| در Redis | نتیجه |
|---|---|
| کدهای یک‌بارمصرف (<span dir="ltr">`otp:{phone}`</span>) | کسی که وسط ورود بود دوباره کد می‌خواهد |
| شمارنده‌های محدودیت نرخ | همه‌ی پنجره‌ها از صفر شروع می‌شوند؛ چند دقیقه کسی می‌تواند بیشتر از سقف درخواست بدهد |
| cache منوی عمومی و نگاشت `qr_token` | از PostgreSQL دوباره ساخته می‌شوند؛ چند دقیقه بار دیتابیس بیشتر است |

## ۵. پشتیبان شبانه (`W4-PA-1`)

برای هر دیتابیس، هر شب، جدا:

1. یک CronJob در `production` با `pg_dump --format=custom` از یک دیتابیس خروجی می‌گیرد.
2. خروجی را رمز می‌کند.
3. آن را در object storage در یک مسیر با تاریخ و نام دیتابیس می‌گذارد.
4. اندازه‌ی فایل و تعداد ردیف چند جدول اصلی را لاگ می‌کند (برای مقایسه در تمرین بازیابی).
5. اگر هر قدم شکست بخورد، job شکست می‌خورد و هشدار «Backup» می‌آید ([فصل ۱۶](16-monitoring-and-alerts.md)).

</div>

```bash
# example: the nightly job for one database (tool names for encryption and upload are illustrative)
set -euo pipefail
FILE="catalog-$(date -u +%Y%m%dT%H%MZ).dump"
pg_dump --format=custom --dbname="$CATALOG_DB_URL" --file="/work/$FILE"
age --recipient "$BACKUP_PUBLIC_KEY" --output "/work/$FILE.age" "/work/$FILE"
# upload /work/$FILE.age to the private backup bucket with an S3-compatible client
rm -f "/work/$FILE"
```

<div dir="rtl">

تصمیم‌هایی که مشخصات فنی نگرفته و `W4-PA-1` می‌گیرد (همه پیشنهاد اولیه):

| موضوع | پیشنهاد اولیه | چرا |
|---|---|---|
| bucket | یک bucket خصوصی جدا، مثلاً `sarmiz-backups`، نه `sarmiz-media` که عمومی است | پشتیبان نباید از CDN خوانده شود |
| رمزنگاری | کلید عمومی/خصوصی؛ job فقط کلید عمومی را دارد و کلید خصوصی بیرون از cluster است | اگر سرور نفوذ شود، پشتیبان‌ها هنوز خواندنی نیستند |
| ساعت | بعد از نیمه‌شب، وقتی کافه‌ها بسته‌اند | کمترین بار روی دیتابیس |
| نگه‌داری | ۷ نسخه‌ی روزانه و ۴ نسخه‌ی هفتگی | یک خرابی دیرکشف‌شده هم قابل برگشت باشد، بدون هزینه‌ی زیاد |
| دسترسی | job فقط اجازه‌ی نوشتن در bucket دارد، نه پاک کردن | راز لورفته‌ی job نتواند پشتیبان‌ها را پاک کند |
| `staging` | پشتیبان ندارد | داده‌اش seed است و با `W2-PA-5` دوباره ساخته می‌شود |

> [!WARNING]
> کلید خصوصی رمزگشایی و کلید AES اطلاعات درگاه را هرگز کنار پشتیبان‌ها و هرگز فقط روی همان سرور نگه ندار. اگر با سرور بروند، پشتیبان‌ها هم بی‌مصرف‌اند. جای امنشان را منتور تعیین می‌کند.

## ۶. تمرین بازیابی (`W5-PA-2`)

هدف: ثابت کنی از پشتیبان دیشب می‌شود هر چهار دیتابیس را برگرداند و ببینی چقدر طول می‌کشد.

> [!CAUTION]
> پشتیبان `production` داده‌ی واقعی کسب‌وکارها و شماره‌ی صاحبانشان را دارد. آن را در `staging` یا روی لپ‌تاپ بازیابی نکن. پیشنهاد اولیه: یک namespace موقت بدون ingress روی cluster که بعد از تمرین کامل پاک می‌شود.

قدم‌ها:

1. **آماده شو.** زمان تمرین را در گروه بگو. زمان‌سنج را روشن کن.
2. **پشتیبان را پیدا کن.** آخرین فایل هر چهار دیتابیس را در bucket پیدا کن. تاریخ و اندازه را با لاگ job دیشب مقایسه کن.
3. **بیاور و رمزگشایی کن.** با کلید خصوصی که از جای امنش آورده‌ای.
4. **دیتابیس خالی بساز.** یک PostgreSQL موقت در namespace تمرین، با چهار دیتابیس و چهار role مثل `production`. افزونه‌ی pgvector را برای `ai` نصب کن.
5. **بازیابی کن:**

</div>

```bash
pg_restore --no-owner --role=catalog --dbname="$RESTORE_CATALOG_URL" catalog-<timestamp>.dump
```

<div dir="rtl">

6. **بسنج:**
   - نسخه‌ی migration در جدول goose با تعداد migrationهای انتشار فعلی همان سرویس یکی است.
   - تعداد ردیف جدول‌های اصلی (`venues`، `menu_items`، `orders`، `payments`، `users`) با عددهای لاگ‌شده‌ی job دیشب یکی است.
   - آخرین `orders.created_at` به زمان پشتیبان نزدیک است.
   - یک نسخه از سرویس‌ها را در همان namespace به دیتابیس‌های بازیابی‌شده وصل کن و منوی کسب‌وکار دمو را بخوان.
7. **زمان را ثبت کن** و با RTO مقایسه کن. یادت باشد این فقط بخش دیتابیس است؛ در فاجعه‌ی واقعی ساختن سرور هم هست.
8. **پاک کن.** namespace تمرین، فایل‌های دانلودشده و رمزگشایی‌شده را پاک کن.
9. **ثبت کن.** نتیجه را در runbook (بخش ۷) و یادداشت آخر هفته بنویس.

چک‌لیست تمرین:

- [ ] هر چهار دیتابیس بدون خطا بازیابی شد.
- [ ] نسخه‌ی migration و تعداد ردیف‌ها با انتظار می‌خواند.
- [ ] سرویس روی دیتابیس بازیابی‌شده بالا آمد و منوی دمو باز شد.
- [ ] رمزگشایی بدون دسترسی به سرور اصلی ممکن بود.
- [ ] زمان کل ثبت شد و زیر ۴ ساعت بود، یا علت و برنامه‌ی کوتاه کردنش نوشته شد.
- [ ] همه‌ی داده‌های موقت پاک شد.

شکل ثبت نتیجه (پیشنهاد اولیه):

</div>

```text
Restore drill: week 5
Backup used: <file names and timestamps>
Databases restored: identity, catalog, orders, ai
Time from start to menu visible: <minutes>
Checks: migration versions OK | row counts OK | demo menu OK
Problems found: <list>
Changes to the runbook: <list>
Done by: <names>
```

## ۷. runbook: ساختاری که زوج پلتفرم کامل می‌کند

runbook یعنی دستورالعمل قدم‌به‌قدمی که آدمی خسته، ساعت ۱۰ شب، بدون فکر کردن اجرا کند. جای فایلش در مشخصات فنی نیامده؛ پیشنهاد اولیه `deploy/RUNBOOK.md` و تعیینش با `W5-PA-2`. این بخش‌ها را داشته باشد:

| بخش | محتوا |
|---|---|
| ۱. چه کسی و چطور | چه کسی تصمیم می‌گیرد (منتور)، چه کسی اجرا می‌کند، چطور با هم تماس بگیرند |
| ۲. کجا چیست | bucket پشتیبان، جای امن رازها و کلید رمزگشایی، پنل ارائه‌دهنده‌ی سرور و DNS (بدون خود رازها) |
| ۳. ساختن سرور تازه | نصب k3s، ingress و cert-manager، با دستورهای دقیق |
| ۴. برگرداندن رازها | از جای امن به Kubernetes secrets، برای هر سرویس |
| ۵. بازیابی دیتابیس‌ها | قدم‌های بخش ۶، برای هر چهار دیتابیس |
| ۶. استقرار | Helm با آخرین tag انتشار، از روی <span dir="ltr">`deploy/`</span> |
| ۷. DNS و TLS | عوض کردن رکوردها، صبر برای گواهی |
| ۸. بررسی | منوی دمو، ثبت سفارش آزمایشی، داشبورد overview، هشدارها |
| ۹. خبر دادن | پیام کوتاه به صاحبان کسب‌وکار: چه شد، چه داده‌ای از دست رفت، چه کاری بکنند |
| ۱۰. سابقه‌ی تمرین‌ها | جدول نتیجه‌ی هر تمرین |

## ۸. outbox هنگام قطعی NATS

وقتی NATS پایین است، سفارش‌ها باز هم ثبت می‌شوند (بخش ۱۶ مشخصات فنی):

1. `order` سفارش و ردیف `outbox` را در یک تراکنش می‌نویسد. به NATS نیازی ندارد.
2. حلقه‌ی relay نمی‌تواند منتشر کند؛ ردیف‌ها با `sent_at` خالی می‌مانند و دوباره تلاش می‌کند.
3. `outbox_lag_seconds` بالا می‌رود و بعد از ۶۰ ثانیه هشدار «Outbox» می‌آید.
4. صفحه‌ی آشپزخانه رویداد زنده نمی‌گیرد، ولی هر ۳۰ ثانیه سفارش‌ها را از API می‌خواند؛ هیچ سفارشی گم نمی‌شود.
5. وقتی NATS برگشت، relay ردیف‌های مانده را به ترتیب منتشر می‌کند. مصرف‌کننده‌ها رویداد تکراری را با `id` رویداد کنار می‌گذارند.

دو نکته برای بازیابی:

- بعد از بازیابی دیتابیس، ردیف‌های `outbox` که در لحظه‌ی پشتیبان فرستاده نشده بودند دوباره منتشر می‌شوند. مصرف‌کننده‌ها باید تکراری را تحمل کنند؛ `realtime` دیتابیس ندارد، ولی صفحه‌ی آشپزخانه وضعیت واقعی را از API می‌خواند، پس یک اعلان تکراری بی‌خطر است.
- اگر NATS داده‌اش را از دست بدهد، رویدادهایی که منتشر شده ولی هنوز مصرف نشده بودند می‌روند. برای <span dir="ltr">`order.*`</span> مهم نیست (polling)؛ ولی یک `menu.changed` گم‌شده یعنی ایندکس دستیار تا تغییر بعدی منو کهنه می‌ماند، و یک `import.requested` گم‌شده یعنی کار import در صف می‌ماند. راه جبران این دو در مشخصات فنی نیامده؛ زوج‌های هسته و پلتفرم در `W5-PA-2` تصمیم می‌گیرند.

## ۹. سناریوهای فاجعه

| سناریو | چه چیزی از دست می‌رود | پاسخ |
|---|---|---|
| سرور از دست رفت | هر چیزی بعد از آخرین پشتیبان، حداکثر ۲۴ ساعت | runbook کامل: سرور تازه، رازها، بازیابی چهار دیتابیس، استقرار، DNS. پرداخت‌های این فاصله در دیتابیس نیستند ولی پول به کسب‌وکار رسیده؛ به صاحبان بگو با پنل درگاه خودشان تطبیق بدهند |
| یک دیتابیس خراب شد | داده‌ی همان سرویس بعد از آخرین پشتیبان | سرویس را به صفر replica ببر (رفتار بخش ۱۶ مشخصات فنی را کاربر می‌بیند)، پشتیبان را در یک دیتابیس تازه بازیابی کن، سرویس را به آن وصل کن. سرویس‌های دیگر کار می‌کنند |
| migration بد | بستگی دارد | اگر فقط schema اضافه کرده: `helm rollback` کد کافی است ([فصل ۱۴](14-ci-cd-and-version-control.md)). اگر داده را خراب کرده: پشتیبان را در دیتابیس موقت بازیابی کن و فقط داده‌ی آسیب‌دیده را با یک اسکریپت بازبینی‌شده برگردان |
| کاربر چیزی را اشتباهی پاک کرد (مثلاً یک دسته‌ی منو) | تغییرات همان بخش بعد از پشتیبان | پشتیبان را در دیتابیس موقت بازیابی کن، ردیف‌های همان `venue_id` را پیدا کن، با اسکریپت SQL بازبینی‌شده برگردان، `menu_version` را بالا ببر تا cache عوض شود، و در `audit_log` ثبت کن |
| رازی لو رفت | اعتماد | فوری عوض کن (جدول پایین)، لاگ‌ها را برای سوءاستفاده بگرد، منتور را خبر کن. پاک کردن از Git کافی نیست |

> [!NOTE]
> اینکه پاک کردن منو در سرمیز «نرم» است (مثلاً با `is_active`) یا واقعاً ردیف را حذف می‌کند، در مشخصات فنی نیامده. پاک کردن نرم بازگرداندن را خیلی ساده‌تر می‌کند؛ زوج هسته در `W2-CORE-1` تصمیم بگیرد.

اگر راز لو رفت، عوض کردن هر کدام چه نتیجه‌ای دارد:

| راز | بعد از عوض کردن |
|---|---|
| کلید امضای JWT | همه‌ی توکن‌ها باطل می‌شوند و همه دوباره وارد می‌شوند |
| رمز role یک دیتابیس | secret و Podهای همان سرویس به‌روز می‌شوند |
| کلید AES اطلاعات درگاه | همه‌ی `credentials_enc`ها باید با کلید تازه دوباره رمز شوند؛ روشش را زوج سفارش در `W4-ORD-1` آماده کند |
| اطلاعات درگاه یک کسب‌وکار | صاحب کسب‌وکار آن را در پنل درگاه عوض می‌کند و در سرمیز دوباره وارد می‌کند |
| کلید سرویس پیامک، کلیدهای object storage، راز header تماس با `ai` | در پنل ارائه‌دهنده باطل کن، تازه بساز، secret را به‌روز کن |
| کلید رمزگشایی پشتیبان | کلید تازه بساز؛ پشتیبان‌های قبلی را با کلید تازه دوباره رمز کن یا زودتر پاکشان کن |

## چک‌لیست انتشار ۱

- [ ] پشتیبان شبانه‌ی هر چهار دیتابیس رمزشده در object storage بیرون از سرور است.
- [ ] مدت نگه‌داری اعمال می‌شود و job حق پاک کردن پشتیبان‌ها را ندارد.
- [ ] هشدار «Backup» با یک شکست ساختگی امتحان شده است.
- [ ] تمرین بازیابی کامل انجام شده، زمانش ثبت شده و زیر ۴ ساعت است.
- [ ] کلید رمزگشایی، کلید AES و بقیه‌ی رازها یک نسخه‌ی امن بیرون از cluster دارند و منتور جایش را می‌داند.
- [ ] runbook همه‌ی ده بخش را دارد و کسی غیر از نویسنده‌اش یک بار آن را خوانده و فهمیده است.
- [ ] راه حفاظت از `sarmiz-media` در برابر پاک شدن اشتباهی انتخاب و ثبت شده است.

## اشتباه‌های رایج

| اشتباه | چرا بد است | چه کار کن |
|---|---|---|
| پشتیبان روی همان سرور | با رفتن سرور، پشتیبان هم می‌رود | object storage بیرون از سرور |
| کلید رمزگشایی کنار پشتیبان | رمز کردن بی‌معنی می‌شود | کلید جدا، بیرون از cluster |
| پشتیبانی که هیچ‌وقت بازیابی نشده | ممکن است خالی یا ناقص باشد و روز فاجعه بفهمی | تمرین بازیابی و تکرارش بعد از تغییرات بزرگ |
| بازیابی پشتیبان `production` در `staging` | داده‌ی واقعی به محیطی می‌رود که برای آن ساخته نشده | namespace موقت و پاک کردن بعد از تمرین |
| `pg_dump` همه‌ی دیتابیس‌ها در یک فایل | نمی‌شود یک سرویس را جدا برگرداند | یک فایل برای هر دیتابیس |
| بازگرداندن کل دیتابیس برای یک دسته‌ی پاک‌شده | داده‌ی همه‌ی کسب‌وکارهای دیگر از آن ساعت تا حالا می‌رود | بازیابی در دیتابیس موقت و برگرداندن فقط همان ردیف‌ها |
| job که شکستش را پنهان می‌کند (بدون `set -e`) | هشدار نمی‌آید و هر شب فایل خالی ساخته می‌شود | هر قدم شکست را بالا بدهد؛ اندازه‌ی فایل را بسنج |
