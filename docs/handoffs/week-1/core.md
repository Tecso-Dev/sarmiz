## ۲. چه چیزی از قبل آماده است

هفته‌ی ۱ اولین هفته است، پس کدی از قبل وجود ندارد. این چیزها را داری:

- طرح پایه‌ی جدول‌های `identity` و `catalog` در بخش ۷ مشخصات فنی. این طرح نقطه‌ی شروع است؛ تو آن را بازبینی و نهایی می‌کنی.
- فهرست متدهای gRPC هر سرویس در بخش ۶٫۲ مشخصات فنی.
- بخش پلتفرم در همین هفته سه چیز می‌سازد که به آن‌ها نیاز داری. با آن‌ها روز اول هماهنگ کن:

| چیزی که لازم داری | کار | تا کی |
|---|---|---|
| محیط محلی با PostgreSQL، Redis و NATS | `W1-PA-1` | روز دوم |
| شاسی مشترک سرویس Go در `libs/go/kit` | `W1-PA-2` | روز سوم |
| ابزار `buf` برای ساختن کد از proto | `W1-PA-3` | روز سوم |

تا وقتی شاسی آماده نشده، روی طرح داده و قرارداد proto کار کن (`W1-CORE-1` و `W1-CORE-4`). این دو به شاسی وابسته نیستند.

## ۴. کارها

### `W1-CORE-1`: نهایی کردن طرح داده

**هدف:** طرح پایه‌ی بخش ۷ مشخصات فنی را برای `identity` و `catalog` بازبینی کنی، ایرادهایش را پیدا کنی و اولین migrationها را بنویسی.

**محدوده:** در این هفته فقط این جدول‌ها را می‌سازی: در `identity` جدول‌های `users`، `memberships`، `refresh_tokens` و `audit_log`؛ در `catalog` جدول‌های `venues`، `branches`، `outbox` و `audit_log`. جدول‌های منو در هفته‌ی ۲ می‌آیند، ولی طرحشان را همین هفته روی کاغذ بازبینی کن تا بعد غافل‌گیر نشوی.

**معیار پذیرش:**

- [ ] migrationها با goose روی یک دیتابیس خالی بالا می‌روند و کامل برمی‌گردند (`up` و `down`).
- [ ] هر جدولِ متعلق به کسب‌وکار ستون `venue_id` و ایندکسی دارد که با `venue_id` شروع می‌شود.
- [ ] نقش دیتابیس هر سرویس فقط به دیتابیس خودش دسترسی دارد. این را با یک تست نشان بده.
- [ ] نمودار جدول‌ها با Mermaid در README هر سرویس هست.
- [ ] هر جا از طرح پایه فاصله گرفتی، یک سند تصمیم در <span dir="ltr">`docs/decisions/`</span> نوشته‌ای.
- [ ] منتور طرح را تأیید کرده است.

**نکته:** متن‌هایی که مهمان می‌بیند به شکل JSONB با کلید زبان ذخیره می‌شوند و پول همیشه `bigint` به ریال است. این دو تصمیم گرفته شده‌اند؛ سراغ عوض کردنشان نرو.

### `W1-CORE-2`: سرویس `identity`

**هدف:** ورود با شماره‌ی موبایل و کد یک‌بارمصرف، با توکن‌هایی که امن نگه‌داری و تازه می‌شوند.

**محدوده:** متدهای `RequestOtp`، `VerifyOtp`، `RefreshToken`، `Logout` و `GetMe`، امضای JWT با Ed25519، و نشانی JWKS برای اینکه `gateway` بتواند توکن را بررسی کند. `IssueStreamTicket` و متدهای `AccessService` به‌جز `GrantMembership` در هفته‌های بعد می‌آیند.

**معیار پذیرش:**

- [ ] کد ۶ رقمی است، ۱۲۰ ثانیه اعتبار دارد و در Redis به شکل hash ذخیره می‌شود، نه متن ساده.
- [ ] بعد از ۵ تلاش اشتباه، آن کد باطل می‌شود.
- [ ] توکن دسترسی ۱۵ دقیقه عمر دارد و claimهای `sub`، `adm` و `mem` را دارد.
- [ ] توکن تازه‌سازی در هر استفاده عوض می‌شود. اگر توکن قدیمی دوباره استفاده شود، کل خانواده‌ی آن باطل می‌شود. برای این حالت تست داری.
- [ ] ارسال پیامک پشت یک interface است. در محیط محلی پیاده‌سازی `console` کد را در لاگ چاپ می‌کند و در هیچ محیط دیگری فعال نمی‌شود.
- [ ] شماره‌ی موبایل در لاگ‌ها پوشیده است و کد و توکن هیچ‌وقت لاگ نمی‌شوند.
- [ ] منطق سرویس تست واحد دارد و مسیر کامل ورود یک تست یکپارچه با PostgreSQL و Redis واقعی دارد.
- [ ] منتور کد را بازبینی کرده است.

**نکته:** محدودیت تعداد درخواست کد (یک بار در ۶۰ ثانیه برای هر شماره) در `gateway` اعمال می‌شود، ولی شمارش تلاش‌های اشتباهِ هر کد کار خود `identity` است.

### `W1-CORE-3`: اسکلت `catalog` و ساخت کسب‌وکار

**هدف:** سرویس `catalog` روی شاسی مشترک بالا بیاید و صاحب کسب‌وکار بتواند اولین کسب‌وکارش را بسازد.

**محدوده:** متدهای `CreateVenue`، `GetVenue` و `ListMyVenues`. هنگام ساخت کسب‌وکار، یک شعبه‌ی پیش‌فرض ساخته می‌شود و `catalog` از `identity` می‌خواهد نقش `owner` را به سازنده بدهد.

**معیار پذیرش:**

- [ ] `CreateVenue` کسب‌وکار و شعبه‌ی پیش‌فرض را در یک تراکنش می‌سازد.
- [ ] اگر دادن نقش در `identity` شکست بخورد، کسب‌وکارِ نیمه‌ساخته باقی نمی‌ماند. این حالت تست دارد.
- [ ] `slug` یکتاست و از نام ساخته می‌شود؛ برخورد نام‌ها خطای `conflict` می‌دهد.
- [ ] یک تابع کمکی وجود دارد که `venue_id` را از metadata مطمئن می‌خواند، و همه‌ی متدهای repository آن را می‌گیرند.
- [ ] اولین تست جداسازی نوشته شده: کاربر کسب‌وکار «الف» با `GetVenue` نمی‌تواند کسب‌وکار «ب» را بگیرد و `not_found` می‌بیند.
- [ ] <span dir="ltr">`/healthz`</span>، <span dir="ltr">`/readyz`</span> و <span dir="ltr">`/metrics`</span> کار می‌کنند.

### `W1-CORE-4`: قرارداد proto

**هدف:** قرارداد دو سرویس برای هفته‌های ۱ و ۲ نوشته و با بخش‌های دیگر توافق شود، تا آن‌ها معطل پیاده‌سازی تو نمانند.

**محدوده:** همه‌ی متدهایی که در هفته‌ی ۱ و ۲ لازم‌اند: ورود، کسب‌وکار، میز، منو، منوی عمومی، `ResolveTable` و `PriceItems`. پیاده‌سازی متدهای هفته‌ی ۲ فعلاً فقط خطای `unimplemented` برمی‌گرداند.

**معیار پذیرش:**

- [ ] فایل‌ها در <span dir="ltr">`proto/sarmiz/identity/v1/`</span> و <span dir="ltr">`proto/sarmiz/catalog/v1/`</span> هستند و `buf lint` بدون خطاست.
- [ ] هر متدی که از بیرون صدا زده می‌شود، annotation مسیر HTTP دارد و با جدول مسیرهای بخش ۶٫۱ مشخصات فنی می‌خواند.
- [ ] قواعد اعتبارسنجی فیلدها با `protovalidate` نوشته شده است.
- [ ] بخش‌های فرانت، سفارش و پلتفرم PR قرارداد را بازبینی و تأیید کرده‌اند.

یک نمونه‌ی کوچک برای اینکه شکل کار را ببینی:

</div>

```proto
service AuthService {
  rpc RequestOtp(RequestOtpRequest) returns (RequestOtpResponse) {
    option (google.api.http) = {
      post: "/api/v1/auth/otp/request"
      body: "*"
    };
  }
}

message RequestOtpRequest {
  string phone = 1 [(buf.validate.field).string.pattern = "^\\+98[0-9]{10}$"];
}
```

## ۵. قرارداد با بخش‌های دیگر

| قرارداد | با چه کسی | قاعده |
|---|---|---|
| فایل‌های proto | همه | بعد از تأیید، هر تغییری PR جدا می‌خواهد و `buf breaking` باید سبز باشد |
| claimهای توکن (`sub`، `adm`، `mem`) | پلتفرم (`gateway`) | نام و شکل claimها را بدون هماهنگی عوض نکن |
| نشانی JWKS | پلتفرم | مسیر و قالب ثابت بماند |
| metadata مطمئن (`x-user-id`، `x-venue-id`، `x-role`) | پلتفرم | `catalog` این‌ها را از `gateway` می‌گیرد و به آن‌ها اعتماد می‌کند |
| `GrantMembership` | داخل خود بخش | فقط `catalog` اجازه دارد صدایش بزند |

## ۶. تصمیم‌های گرفته‌شده

این‌ها را دوباره باز نکن. اگر فکر می‌کنی اشتباه‌اند، با منتور حرف بزن و سند تصمیم بنویس.

- هر سرویس دیتابیس خودش را دارد و سرویس دیگر به آن دست نمی‌زند: [سند تصمیم ۳](../../decisions/0003-database-per-service.md).
- متن چندزبانه به شکل JSONB ذخیره می‌شود: [سند تصمیم ۵](../../decisions/0005-i18n-as-jsonb.md).
- توکن با Ed25519 امضا می‌شود و در کوکی `HttpOnly` می‌نشیند، نه در `localStorage`.
- نقش‌ها سه‌تا هستند: `owner`، `manager` و `staff`. در انتشار ۱ فقط `owner` ساخته می‌شود، ولی جدول و بررسی‌ها از همین حالا هر سه را می‌شناسند.
- منبعی که متعلق به کسب‌وکار دیگری است خطای `not_found` می‌دهد، نه `permission_denied`.

## ۷. دام‌های رایج

| دام | چرا بد است | چه کار کن |
|---|---|---|
| ذخیره‌ی کد یک‌بارمصرف به شکل متن ساده | هر کس به Redis برسد می‌تواند وارد حساب دیگران شود | فقط hash کد را نگه دار |
| جواب متفاوت برای شماره‌ی ثبت‌نام‌شده و نشده | می‌شود فهمید چه کسی مشتری سرمیز است | `RequestOtp` همیشه یک جواب بدهد |

| migration که برنمی‌گردد | استقرار خراب را نمی‌شود عقب برد | هر migration را با `down` امتحان کن |

**از دستیار نخواه:**

- که خودش درباره‌ی شکل claimها، نام جدول‌ها یا مسیرها تصمیم بگیرد. این‌ها در مشخصات فنی هستند.
- که الگوریتم رمزنگاری یا تولید عدد تصادفی را خودش پیاده کند. از کتابخانه‌ی استاندارد Go استفاده کن (`crypto/rand`، `crypto/ed25519`، `crypto/subtle`).
- که چند کار را در یک PR انجام دهد.

**خودت حتماً بررسی کن:** هر خط کد ورود را باید بتوانی برای منتور توضیح بدهی. اگر دستیار چیزی نوشت که نمی‌فهمی، بپرس «این خط چرا لازم است و اگر حذفش کنم چه می‌شود؟» و جواب را با مشخصات فنی مقایسه کن.

## ۹. چطور بفهمی درست کار می‌کند

این سناریو را آخر هفته روی `staging` اجرا کن. همین سناریو بخشی از دموی هفته است.

1. `POST /api/v1/auth/otp/request` با یک شماره‌ی آزمایشی. جواب موفق می‌گیری.
2. همان درخواست را بلافاصله تکرار کن. باید خطای `rate_limited` بگیری.
3. کد را از سرویس پیامک آزمایشی بردار و `POST /api/v1/auth/otp/verify` را صدا بزن. دو کوکی `sz_at` و `sz_rt` تنظیم می‌شوند.
4. `GET /api/v1/me` نام و شماره‌ی پوشیده‌ات را می‌دهد و فهرست نقش‌ها خالی است.
5. `POST /api/v1/venues` یک کسب‌وکار می‌سازد.
6. `POST /api/v1/auth/refresh` و بعد دوباره `GET /api/v1/me`: حالا نقش `owner` برای همان کسب‌وکار دیده می‌شود.
7. با یک کاربر دوم وارد شو و <span dir="ltr">`GET /api/v1/venues/{venue_id}`</span> کسب‌وکار اول را بخواه. باید `not_found` بگیری.
8. در Grafana یا لاگ‌ها بگرد: نباید هیچ کد، توکن یا شماره‌ی کاملی پیدا کنی.
