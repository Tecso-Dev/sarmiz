## ۲. چه چیزی از قبل آماده است

هفته‌ی ۱ اولین هفته است و کدی از قبل نیست. از هفته‌ی صفر، منتور سرور داخل ایران با دسترسی SSH، دامنه (اگر تصمیم باز ۱ بسته شده باشد)، عکس ۵ منوی کاغذی واقعی، حساب سرویس پیامک و گروه هشدار را آماده کرده است. فهرست کامل در [تحویل منتور](../week-0-mentor.md) است.

**صاحب کارها:** در طرح سه‌نفره کارهای این صفحه بین دو نقش تقسیم شده‌اند و `W1-PA-7` به انتشار ۲ رفته است. جدول بالای صفحه می‌گوید هر کار مال کدام نقش است و در کدام هفته انجام می‌شود. روزهای اول همه منتظر محیط محلی، شاسی و `buf` هستند؛ اگر صاحبشان عقب افتاد، همان روز در گروه تیم بگوید.

## ۴. کارها

### `W1-PA-1`: محیط محلی

**هدف:** هر عضو تیم با یک دستور همه‌ی زیرساخت محلی را بالا بیاورد.

**محدوده:** Docker Compose برای PostgreSQL با چهار دیتابیس و چهار role، Redis، NATS JetStream و MinIO؛ Ollama به‌صورت اختیاری؛ Makefile و <span dir="ltr">`.env.example`</span>.

**معیار پذیرش:**

- [ ] یک دستور (مثلاً `make up`) همه را بالا می‌آورد و هر container یک healthcheck دارد.
- [ ] دیتابیس‌های `identity`، `catalog`، `orders` و `ai` هر کدام role خودشان را دارند و یک اسکریپت نشان می‌دهد هر role به دیتابیس دیگر وصل نمی‌شود.
- [ ] دیتابیس `ai` افزونه‌ی pgvector را دارد.
- [ ] bucketهای `sarmiz-media` و `sarmiz-imports` در MinIO ساخته می‌شوند.
- [ ] <span dir="ltr">`.env.example`</span> فقط نام متغیرها را دارد و <span dir="ltr">`.env`</span> در <span dir="ltr">`.gitignore`</span> است.
- [ ] جدول «Commands» در `AGENTS.md` برای بالا آوردن زیرساخت به‌روز شده است.
- [ ] یک نفر از بخش دیگر روی ماشین خودش از clone تازه تا محیط آماده رفته و مشکلی نداشته است.

### `W1-PA-2`: شاسی مشترک Go

**هدف:** هر سرویس Go با چند خط کد، config و لاگ و سرور gRPC و health و خاموش شدن درست داشته باشد، بدون اینکه کسی این‌ها را دوباره بنویسد.

**محدوده:** پکیج‌های `libs/go/kit` برای config، لاگ JSON با `log/slog`، راه‌اندازی سرور gRPC با interceptorهای request id، recovery، لاگ، metric و trace، health، خاموش شدن آرام، نگاشت خطا، و کمکی‌های pgx و Redis. بخش رویدادها را بخش سفارش در `W1-ORD-4` اضافه می‌کند.

**معیار پذیرش:**

- [ ] config از متغیر محیطی خوانده می‌شود و اگر متغیر لازمی نباشد سرویس با پیام روشن بالا نمی‌آید.
- [ ] هر خط لاگ JSON است و فیلدهای بخش ۱۲ مشخصات فنی را دارد؛ یک کمکی شماره‌ی موبایل را پوشیده می‌کند.
- [ ] interceptorها request id را از metadata می‌خوانند یا می‌سازند، panic را به `internal` تبدیل می‌کنند و برای هر متد metric نرخ، خطا و مدت ثبت می‌کنند.
- [ ] <span dir="ltr">`/healthz`</span>، <span dir="ltr">`/readyz`</span>، <span dir="ltr">`/metrics`</span> و سرویس health در gRPC با یک فراخوانی راه می‌افتند.
- [ ] با `SIGTERM` سرویس درخواست تازه نمی‌گیرد و درخواست‌های در جریان را تا یک مهلت تمام می‌کند. تست دارد.
- [ ] نگاشت خطای دامنه به کد gRPC فقط در یک جاست و پیام داخلی به بیرون نمی‌رود.
- [ ] pool پیش‌فرض pgx ده اتصال دارد و تست‌ها با <span dir="ltr">`-race`</span> سبزند.
- [ ] `libs/go/kit/README.md` قالب «سرویس تازه» را قدم‌به‌قدم دارد و بخش‌های هسته و سفارش آن را بازبینی و تأیید کرده‌اند.

**نکته:** خروجی trace به Tempo کار هفته‌ی ۳ است (`W3-PA-1`). این هفته فقط زمینه‌ی W3C را از metadata بگیر و جلو ببر، تا بعداً فقط exporter وصل شود.

### `W1-PA-3`: ابزار Protobuf

**هدف:** قرارداد هر سرویس فقط در proto نوشته شود و بقیه‌ی چیزها از آن ساخته شوند.

**محدوده:** ساختار <span dir="ltr">`proto/sarmiz/<service>/v1/`</span>، `buf.yaml`، lint، بررسی تغییر ناسازگار، تولید کد Go، grpc-gateway، OpenAPI و stubهای Python، و commit کردن OpenAPI در `docs/api/openapi.yaml`.

**معیار پذیرش:**

- [ ] `buf lint` و `buf breaking` (در مقایسه با `main`) در CI روی هر PR که <span dir="ltr">`proto/`</span> را عوض کند اجرا می‌شوند.
- [ ] یک دستور، کد Go، grpc-gateway، OpenAPI و stubهای Python را می‌سازد و در `AGENTS.md` نوشته شده است.
- [ ] `docs/api/openapi.yaml` از proto ساخته و commit می‌شود و CI اگر کهنه باشد شکست می‌خورد.
- [ ] `protovalidate` در دسترس است و یک نمونه‌ی کار‌کرده در `proto/README.md` هست.
- [ ] تولید کد بدون نیاز به سرویس بیرونی کار می‌کند.
- [ ] `proto/README.md` می‌گوید سرویس تازه چطور اضافه می‌شود و قاعده‌ی «فیلد را هیچ‌وقت دوباره شماره نده» را دارد.

**نکته:** اینکه کد Go تولیدشده commit شود یا فقط در CI ساخته شود را مشخصات فنی نگفته است. پیشنهاد اولیه: commit شود تا `go build` بدون `buf` کار کند. pluginهای راه دور `buf` ممکن است از داخل ایران در دسترس نباشند؛ pluginها را محلی نصب کن.

### `W1-PA-4`: اسکلت `gateway`

**هدف:** مرورگر از یک در وارد شود و همان در توکن، Origin و قالب خطا را درست کند.

**محدوده:** grpc-gateway وصل به `identity` برای <span dir="ltr">`/api/v1/auth/*`</span> و <span dir="ltr">`/api/v1/me`</span>، و به `catalog` برای مسیرهای کسب‌وکار که دموی هفته لازم دارد؛ بررسی JWT با JWKS، allowlist برای CORS، بررسی Origin، request id و قالب یکسان خطا. مسیرهای کامل، نقش‌ها و همه‌ی محدودیت‌های نرخ در `W2-PA-1` می‌آیند. فقط محدودیت درخواست کد (یک بار در ۶۰ ثانیه برای هر شماره) از همین هفته لازم است، چون دموی هسته آن را می‌سنجد.

**معیار پذیرش:**

- [ ] توکن از کوکی `sz_at` خوانده می‌شود، فقط الگوریتم Ed25519 پذیرفته می‌شود و JWKS ده دقیقه در حافظه می‌ماند.
- [ ] درخواست ناامن (`POST`، `PUT`، `PATCH`، `DELETE`) با Origin بیرون از allowlist رد می‌شود.
- [ ] هر پاسخ header شناسه‌ی درخواست را دارد و همان شناسه به‌صورت `x-request-id` به سرویس می‌رسد.
- [ ] همه‌ی خطاها، حتی مسیر ناموجود، قالب بخش ۶٫۱ را دارند و جزئیات داخلی بیرون نمی‌رود.
- [ ] `x-user-id` فقط از توکن بررسی‌شده ساخته می‌شود و header هم‌نام از بیرون دور ریخته می‌شود.
- [ ] بدنه‌ی JSON بزرگ‌تر از ۱ MB رد می‌شود.
- [ ] تست‌ها توکن منقضی، امضای نادرست و الگوریتم دیگر را رد می‌کنند.

**نکته:** مشخصات فنی نگفته کوکی‌ها را چه کسی تنظیم می‌کند. پیشنهاد اولیه: `identity` توکن‌ها را در پاسخ gRPC برمی‌گرداند و `gateway` آن‌ها را به `Set-Cookie` تبدیل و از بدنه حذف می‌کند، تا JavaScript هیچ‌وقت توکن را نبیند. روز اول با بخش هسته قطعی کن.

### `W1-PA-5`: CI

**هدف:** هر PR پیش از ادغام خودکار سنجیده شود و هر ادغام به `main` یک image آماده بسازد.

**محدوده:** lint، تست و build برای هر سرویس با فیلتر مسیر، بررسی `buf`، بررسی مستندات، gitleaks، و ساخت و push image با برچسب git SHA بعد از ادغام.

**معیار پذیرش:**

- [ ] PR که فقط <span dir="ltr">`services/order/`</span> را عوض کرده، فقط lint و تست و build همان سرویس (و شاسی، اگر عوض شده) را اجرا می‌کند.
- [ ] golangci-lint، ESLint و Ruff هر کدام برای بخش خودشان اجرا می‌شوند.
- [ ] `scripts/check-markdown.py` و `scripts/check-links.py` روی هر PR اجرا می‌شوند.
- [ ] gitleaks روی هر PR اجرا می‌شود و یک راز آزمایشی را واقعاً می‌گیرد.
- [ ] بعد از ادغام به `main`، image هر سرویس تغییرکرده با برچسب git SHA ساخته و به registry فرستاده می‌شود.
- [ ] هیچ رازی در فایل‌های workflow نیست؛ همه از GitHub secrets می‌آیند.

### `W1-PA-6`: cluster و استقرار

**هدف:** هر ادغام به `main` بدون دخالت دست روی `staging` بنشیند، با دامنه و TLS واقعی.

**محدوده:** k3s روی سرور، ingress، cert-manager، namespaceهای `staging` و `production`، یک Helm chart عمومی برای سرویس‌های Go، استقرار خودکار `staging`، و بررسی دسترسی سرور به image registry.

**معیار پذیرش:**

- [ ] ingress مسیر <span dir="ltr">`/api/v1/*`</span> را به `gateway`، <span dir="ltr">`/ws`</span> را به `realtime` و بقیه را به `web` می‌فرستد؛ هیچ سرویس دیگری از بیرون در دسترس نیست.
- [ ] گواهی TLS با cert-manager صادر شده و مرورگر هشداری نشان نمی‌دهد.
- [ ] یک chart عمومی در <span dir="ltr">`deploy/helm/`</span> همه‌ی سرویس‌های Go را با فایل values جدا مستقر می‌کند و migration را به‌صورت job پیش از ارتقا اجرا می‌کند.
- [ ] هر ادغام به `main` سرویس تغییرکرده را خودکار روی `staging` مستقر می‌کند.
- [ ] نتیجه‌ی بررسی دسترسی سرور به registry، و راه جایگزین اگر در دسترس نبود، در `deploy/README.md` نوشته شده است.
- [ ] رازها فقط در Kubernetes secrets هستند و `deploy/README.md` نامشان را دارد، نه مقدارشان.
- [ ] نسخه‌ی «سلام» هر هفت جزء (`gateway`، `identity`، `catalog`، `order`، `realtime`، `ai`، `web`) روی `staging` بالاست.

**نکته:** chart عمومی برای سرویس‌های Go است. `web` و `ai` شکل دیگری دارند؛ پیشنهاد اولیه یک chart کوچک جدا برای هر کدام است.

### `W1-PA-7`: ارزیابی AI و اسکلت سرویس `ai`

**هدف:** با عدد بفهمیم مدل محلی منوی فارسی را از عکس می‌خواند و به چهار زبان ترجمه می‌کند یا نه، و سرویس `ai` روی پایه‌ی درست شروع شود.

**محدوده:** اپ FastAPI با health و metric، interface `LLMProvider` (chat، vision، embeddings) با پیاده‌سازی Ollama، تست با provider جعلی، ارزیابی روی ۵ منوی واقعی، و گزارش در `docs/ai/evaluation-week1.md`.

**معیار پذیرش:**

- [ ] <span dir="ltr">`/healthz`</span>، <span dir="ltr">`/readyz`</span> و <span dir="ltr">`/metrics`</span> کار می‌کنند و بقیه‌ی endpointها بدون header راز مشترک رد می‌شوند.
- [ ] همه‌ی دسترسی به مدل از `LLMProvider` می‌گذرد و خروجی مدل با Pydantic اعتبارسنجی می‌شود.
- [ ] تست‌های pytest با provider جعلی در CI سبزند و Ruff خطا ندارد.
- [ ] برای هر ۵ منو، دقت خواندن نام آیتم‌ها و قیمت‌ها، زمان هر عکس و حافظه‌ی مصرفی اندازه‌گیری شده است.
- [ ] ترجمه‌ی یک نمونه‌ی ثابت از متن منوها به `en`، `ar`، `ckb` و `azb` را یک خواننده‌ی آشنا با هر زبان نمره داده است.
- [ ] گزارش نام و اندازه‌ی مدل‌ها، سخت‌افزار، عددها، پیشنهاد «برو» یا «نرو» برای ساخت منو از عکس، و پیشنهاد درباره‌ی سرور جدای مدل را دارد.

**نکته:** معیار عددی «برو» در مشخصات فنی نیامده است. پیشنهاد اولیه را قبل از اجرا با منتور بنویس، مثلاً درصد آیتم‌هایی که نام و قیمتشان درست خوانده شده، تا نتیجه بعداً تفسیر سلیقه‌ای نشود. عکس منوها را بدون اجازه‌ی منتور در ریپو commit نکن و به هیچ سرویس AI بیرونی نده.

## ۵. قرارداد با بخش‌های دیگر

| قرارداد | با چه کسی | قاعده |
|---|---|---|
| API عمومی `libs/go/kit` | هسته، سفارش | بعد از ادغام، امضای تابع را بدون خبر عوض نکن؛ تغییر ناسازگار را در PR جدا و با بازبینی صاحب هر دو بخش بفرست |
| metadata مطمئن (`x-request-id`، `x-user-id` و بعداً `x-venue-id` و `x-role`) | هسته، سفارش | نام‌ها همان بخش ۶٫۲ مشخصات فنی‌اند |
| تنظیم کوکی‌ها | هسته | تصمیم پیشنهاد اولیه‌ی `W1-PA-4` را با هسته ثبت کن |
| `docs/api/openapi.yaml` | فرانت | فقط از proto ساخته می‌شود؛ دستی ویرایش نمی‌شود |
| مسیرهای ingress | سفارش، فرانت | <span dir="ltr">`/api/v1/*`</span>، <span dir="ltr">`/ws`</span> و بقیه؛ بدون هماهنگی عوض نکن |
| قالب image و پورت‌ها در chart | همه | هر سرویس Go پورت gRPC و HTTP را از config می‌گیرد |
| `LLMProvider` | هسته (در هفته‌ی ۳ برای ترجمه) | interface را ساده نگه دار و هر تغییرش را در `docs/ai/README.md` بنویس |

## ۶. تصمیم‌های گرفته‌شده

این‌ها را دوباره باز نکن. اگر فکر می‌کنی اشتباه‌اند، با منتور حرف بزن و سند تصمیم بنویس.

- یک سرور داخل ایران با k3s و دو namespace، و یک chart عمومی برای سرویس‌های Go.
- `gateway` از annotationهای proto ساخته می‌شود و منطق کسب‌وکار ندارد.
- هر سرویس دیتابیس و role خودش را دارد: [سند تصمیم ۳](../../decisions/0003-database-per-service.md).
- همه‌ی دسترسی به مدل از `LLMProvider` می‌گذرد و تست‌های واحد هیچ‌وقت مدل واقعی را صدا نمی‌زنند.
- رازها فقط در Kubernetes secrets و GitHub secrets.

| CI بدون فیلتر مسیر | هر PR بیست دقیقه منتظر می‌ماند و کسی صبر نمی‌کند | فیلتر مسیر از روز اول |
| کشیدن image یا مدل از سرویس خارجی هنگام استقرار | با قطع اینترنت بین‌الملل استقرار می‌خوابد | روز اول دسترسی را بسنج و راه جایگزین را بنویس |

| ارزیابی AI روی یک منوی تمیز | عدد خوب می‌گیری و در کافه‌ی واقعی شکست می‌خوری | همان ۵ عکس واقعی، با نور و خط بد |

## ۹. چطور بفهمی درست کار می‌کند

این سناریو را آخر هفته روی سرور واقعی اجرا کن. همین سناریو بخشی از دموی هفته است.

1. <span dir="ltr">`https://<دامنه>/`</span> را روی گوشی باز کن. گواهی معتبر است و صفحه‌ی «سلام» وب بالا می‌آید. `kubectl get pods -n staging` هر هفت جزء را در حالت `Running` نشان می‌دهد.
2. یک تغییر کوچک در <span dir="ltr">`services/gateway/`</span> را در یک PR بفرست. فقط کارهای CI همان سرویس اجرا می‌شوند.
3. PR را ادغام کن. چند دقیقه بعد `kubectl get deploy -n staging -o wide` image با git SHA تازه را نشان می‌دهد.
4. `curl -i https://<دامنه>/api/v1/me` بدون کوکی: `401` با قالب خطای بخش ۶٫۱ و header شناسه‌ی درخواست.
5. یک `POST` با Origin بیگانه بفرست. رد می‌شود.
6. سناریوی ورود هسته را از راه `gateway` اجرا کن و درخواست دوم کد را در کمتر از ۶۰ ثانیه بفرست؛ `rate_limited` می‌گیری.
7. لاگ `gateway` را بخوان: هر خط JSON است، شناسه‌ی درخواست دارد و هیچ توکن یا شماره‌ی کاملی در آن نیست.
8. گزارش `docs/ai/evaluation-week1.md` را در دمو باز کن و عددها و پیشنهاد «برو» یا «نرو» را توضیح بده.
